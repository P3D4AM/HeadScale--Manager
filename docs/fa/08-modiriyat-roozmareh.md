## در این فصل یاد می‌گیرید

- با یک دستور، وضعیت کامل سرور را ببینید (`hsctl status`)
- چکاپ سلامت دوره‌ای انجام دهید و مشکلات را زود پیدا کنید (`hsctl doctor`)
- کاربر و دستگاه مدیریت کنید و دستگاه ازدست‌رفته را به‌صورت ایمن حذف کنید
- کلید از پیش تأییدشده (Preauth Key) بسازید و نکته امنیتی آن را بدانید
- مسیر شبکه دفتر (Route) را تأیید یا لغو کنید
- پشتیبان بگیرید، راستی‌آزمایی کنید و در زمان نیاز بازیابی کنید
- امن و «نسخه‌به‌نسخه» به‌روزرسانی کنید
- دامنه سرور را عوض کنید و کل سرویس را به یک سرور مجازی (VPS) جدید منتقل کنید

این فصل، جعبه‌ابزار روزمره شماست. نصب که تمام شد (فصل چهارم) و دستگاه‌ها وصل شدند (فصل پنجم و ششم)، بیشترِ کارتان با **ابزار `hsctl`** است که روی سرور اجرا می‌شود.

> 💡 **دو نکته قبل از شروع:** ۱) دستورهایی که چیزی را **تغییر می‌دهند** با `sudo` نوشته شده‌اند؛ اگر لازم باشد و بدون sudo اجرا شود، خودِ hsctl یادآوری می‌کند. ۲) خروجی‌های این فصل **نمونه**‌اند و روی سیستم شما جزئیات‌شان متفاوت است.

اولین دستور هر روز:

```bash

```

نسخه Headscale:          0.29.5
سرویس headscale:         ● فعال و در حال اجرا
دامنه سرور:              https://headscale.example.com
Reverse Proxy (Caddy):   ● فعال و در حال اجرا
فایروال (UFW):           فعال
کاربران:                 3

سلامت سرویس، دامنه، وضعیت پروکسی معکوس (Reverse Proxy) یعنی Caddy، فایروال، تعداد کاربران و دستگاه‌ها، آخرین پشتیبان و فضای دیسک — همه در یک صفحه. اگر چیزی قرمز بود، سراغ دستور بعدی بروید.

## چکاپ سلامت خودکار: `hsctl doctor`

`doctor` مثل یک پزشک عمومی سرور را معاینه می‌کند و برای هر مشکل، خروجی را **در چهار بخش** می‌دهد: **مشکل** (چه چیزی خراب است) / **علت احتمالی** (چرا معمولاً رخ می‌دهد) / **چگونه بررسی شد** (کدام بررسی این نتیجه را داده) / **راهکار** (چه کاری انجام دهید).

```bash
hsctl doctor
```

```text
در حال اجرای بررسی‌های سلامت … (۱۲ از ۱۲ بررسی انجام شد)

✖ مشکل: سرویس headscale اجرا نمی‌شود
   علت احتمالی: توقف غیرمنتظره سرویس یا خطا در فایل پیکربندی
   چگونه بررسی شد: systemctl is-active headscale → پاسخ «inactive»
   راهکار: sudo systemctl start headscale
   اگر دوباره متوقف شد: hsctl config validate و سپس hsctl logs --lines 100

خلاصه: ۱ مشکل پیدا شد (۱۱ مورد سالم بود).
برای تلاش برای رفع خودکارِ مشکلات قابل‌رفع: hsctl doctor --fix
```

وقتی همه‌چیز سالم است، در پایان می‌بینید: `خلاصه: هیچ مشکلی پیدا نشد ✅`

- `hsctl doctor --fix` مشکلات ساده (مثل سرویس خاموش) را خودش رفع می‌کند.
- `hsctl doctor --json` خروجی ساخت‌یافته برای ابزارهای دیگر می‌دهد — برای شما لازم نیست.
- قانون طلایی عیب‌یابی (فصل نهم) همین است: **همیشه اول `doctor`**.

## خواندن لاگ‌ها: `hsctl logs`

لاگ (Log) یعنی دفترچه خاطرات سرویس؛ هر رخداد مهمی آنجا ثبت شده است.

```bash
hsctl logs --lines 100
```

```text
نمایش ۱۰۰ خط آخر لاگ سرویس headscale:
2025-01-15T10:12:03+03:30 INF Headscale launched
2025-01-15T10:13:41+03:30 INF New node registered: phone-sara
2025-01-15T10:40:02+03:30 WRN Node key could not be found in database
2025-01-15T10:41:10+03:30 INF Node authenticated: laptop-reza
راهنما: INF=اطلاعات عادی، WRN=هشدار، ERR=خطا
```

سه شکل کاربردی:

```bash
hsctl logs --lines 100     # ۱۰۰ خط آخر
hsctl logs --since 1h      # رخدادهای یک ساعت گذشته
hsctl logs --follow        # نمایش زنده؛ با Ctrl+C قطع کنید
```

معمولاً باید بیشترِ خط‌ها `INF` باشند؛ `ERR` مکرر یعنی وقت بازکردن فصل نهم است.

## مدیریت کاربران

«کاربر» یعنی یک حساب روی سرور که دستگاه‌ها زیر آن ثبت می‌شوند — مثلاً هر همکار شما یک کاربر.

```bash
hsctl users list
sudo hsctl users create sara
sudo hsctl users delete sara
```

خروجی `list` (ستون‌ها مطابق موتور Headscale):

```text
ID   Name       Username   Email   Created
1    admin      admin      -       2025-01-10
2    reza       reza       -       2025-01-11
3    sara       sara       -       2025-01-15
```

حذف با نام یا شناسه عددی انجام می‌شود و چون دستگاه‌های زیر آن کاربر هم حذف می‌شوند، ابزار قبل از انجام **تأیید** می‌گیرد (`--yes` برای ردکردن تأیید است — فقط وقتی مطمئنید):

```text
⚠ کاربر «sara» به‌همراه ۲ دستگاه ثبت‌شده زیر آن حذف شود؟
این عمل قابل بازگشت نیست. [y/N]
```

## مدیریت دستگاه‌ها

هر گوشی، لپ‌تاپ یا سروری که به شبکه وصل شده، یک «دستگاه» (گره/Node) است.

```bash
hsctl devices list
```

```text
ID   نام دستگاه       کاربر    IP تونل       آخرین دیدن     وضعیت
1    office-router    admin    100.64.0.1    ۱ دقیقه پیش    متصل ✓
2    laptop-reza      reza     100.64.0.2    ۱ ساعت پیش     متصل ✓
3    phone-sara       sara     100.64.0.3    ۳ روز پیش      قطع
```

حذف با **شماره ID** انجام می‌شود و ابزار قبل از اجرا، نام و IP دستگاه را نشان می‌دهد و تأیید می‌خواهد:

```bash
sudo hsctl devices delete 3
```

```text
دستگاه «phone-sara» (ID: 3، IP: 100.64.0.3) حذف شود؟
این عمل قابل بازگشت نیست. [y/N]
```

> ⚠️ **قبل از تأیید حذف، یک لحظه بایستید:** شماره ID و نام دستگاه همان است که می‌خواهید؟ و یادتان باشد «قطع» به‌تنهایی دلیل حذف نیست — دستگاه موقتاً خاموش، بعد از روشن‌شدن برمی‌گردد. حذف فقط برای دستگاه‌هایی است که دیگر نمی‌خواهید یا از دست رفته‌اند.

## کلید از پیش تأییدشده (Preauth Key)

کلید از پیش تأییدشده (Preauth Key) مثل «کد دعوت» است؛ دستگاه جدید با واردکردن آن در زمان اتصال، بدون تعامل اضافه ثبت می‌شود. ساخت کلیدِ قابل‌استفاده‌مجدد با ۲۴ ساعت اعتبار برای کاربر admin:

```bash
sudo hsctl preauth create admin --reusable --expiration 24h
```

```text
کلید از پیش تأییدشده برای کاربر «admin» ساخته شد:

    <AUTH_KEY>

تنظیمات: قابل استفاده مجدد = بله | اعتبار = 24h
```

و استفاده از آن روی دستگاه جدید:

```bash
sudo tailscale up --login-server https://headscale.example.com --authkey <AUTH_KEY>
```

> 🔐 **نکته امنیتی بسیار مهم:**
> - کلید **فقط همین یک‌بار** نشان داده می‌شود؛ اگر کپی‌اش نکنید و صفحه بسته شود، باید کلید جدید بسازید (محدودیت عمدی و برای امنیت شما).
> - کلید را با پیامک/ایمیل **رمزنشده** نفرستید؛ ترجیحاً خودتان وارد کنید.
> - فقط تا حد نیاز اعتبار بدهید: برای یک گوشی، کلید یک‌بارمصرف بدون `--reusable` و با انقضای کوتاه بسازید.

لیست کلیدهای یک کاربر (خودِ کلیدها دیگر نمایش داده نمی‌شوند):

```bash
hsctl preauth list admin
```

```text
ID   اعتبار   قابل استفاده مجدد   وضعیت
4    24h      بله                فعال — ۲ بار استفاده شده
5    1h       خیر                مصرف‌شده
```

## مدیریت مسیرها (Route)

مسیر (Route) همان «جاده‌ای» است که ترافیک تونل را به شبکه دفتر می‌رساند (مفهوم کامل: فصل ششم). بعد از راه‌اندازی ساب‌نت‌روتر (Subnet Router) در دفتر، مسیرش باید روی سرور تأیید شود:

```bash
hsctl routes list
```

```text
ID   دستگاه          موجود (Advertised)   تأییدشده (Approved)   فعال
1    office-router   192.168.1.0/24       —                    —
```

ستون «موجود» یعنی دستگاه دفتر مسیر را پیشنهاد داده؛ تا «تأیید» نشود هیچ کلاینتی از آن استفاده نمی‌کند:

```bash
sudo hsctl routes approve 1 --routes 192.168.1.0/24
```

چند مسیر را با کاما جدا کنید: `--routes 192.168.1.0/24,10.10.0.0/24` — و لغو همه مسیرهای تأییدشده یک دستگاه (وقتی دستگاه دفتر را از کار انداختید):

```bash
sudo hsctl routes revoke 1
```

> 💡 روی کلاینت‌های لینوکسی، پذیرش مسیرها یک‌بار لازم است: `sudo tailscale set --accept-routes` (ویندوز و اندروید خودکار می‌پذیرند).

## پشتیبان‌گیری و بازیابی

پشتیبان، بیمه‌نامه شبکه شماست. hsctl همه چیز ضروری را با هم بسته‌بندی می‌کند: پیکربندی `/etc/headscale/`، پایگاه‌داده و کلیدهای `/var/lib/headscale/`، بلوک Caddy، وضعیت ابزار در `/etc/hem/` و فایل شناسنامه (manifest) با نسخه‌ها و تاریخ.

```bash
sudo hsctl backup create
hsctl backup list
```

```text
در حال ساخت پشتیبان …
پشتیبان ساخته شد: /var/backups/hem/hem-backup-20250115-101530.tar.gz (2.4 MB)

نام فایل                             تاریخ               حجم
hem-backup-20250115-101530.tar.gz    2025-01-15 10:15    2.4 MB
hem-backup-20250112-093000.tar.gz    2025-01-12 09:30    2.3 MB
```

**راستی‌آزمایی** — قبل از اتکا به هر پشتیبان:

```bash
hsctl backup verify hem-backup-20250115-101530.tar.gz
```

```text
✔ آرشیو سالم و قابل بازکردن است
✔ manifest.json موجود است (headscale 0.29.5 — تاریخ: 2025-01-15)
✔ پایگاه‌داده db.sqlite موجود است
✔ کلیدهای سرور موجودند
نتیجه: پشتیبان معتبر است ✅
```

**بازیابی** — وضعیت فعلی سرور را با محتوای پشتیبان جایگزین می‌کند؛ به همین دلیل اول تأیید می‌خواهد، بعد سرویس را متوقف، فایل‌ها را برمی‌گرداند و دوباره اجرا می‌کند:

```bash
sudo hsctl restore hem-backup-20250115-101530.tar.gz
```

پس از پایان، با `hsctl status` و `hsctl doctor` سلامت را چک کنید.

> 💡 عادت خوب: بعد از هر تغییر مهم (کاربر جدید، تأیید مسیر، به‌روزرسانی) یک `backup create` و بعدش `backup verify` — کل کار چند ثانیه بیشتر طول نمی‌کشد.

## به‌روزرسانی امن

اول فقط خبر بگیرید — این دستور **هیچ چیزی را تغییر نمی‌دهد**:

```bash
hsctl update --check
```

```text
نسخه نصب‌شده Headscale:  0.29.5
آخرین نسخه پایدار:       0.29.5
نتیجه: به‌روزرسانی لازم نیست.
```

اگر نسخه جدیدی بود، `sudo hsctl update` کل فرایند را **در پنج مرحله امن** انجام می‌دهد:

| مرحله | چه اتفاقی می‌افتد |
|---|---|
| ۱. توقف | سرویس به‌صورت تمیز متوقف می‌شود |
| ۲. پشتیبان | از وضعیت فعلی پشتیبان گرفته می‌شود |
| ۳. نصب | نسخه جدید نصب می‌شود |
| ۴. پیکربندی | فایل پیکربندی با نسخه جدید مقایسه و در صورت نیاز به‌روز می‌شود |
| ۵. اجرا | سرویس دوباره اجرا و بررسی می‌شود |

> ⚠️ **قید مهم «نسخه‌به‌نسخه»:** ارتقا باید پله‌پله انجام شود (مثلاً 0.27 → 0.28 → 0.29) و **پرش از یک نسخهٔ کوچک به چند نسخه جلوتر مجاز نیست.** اگر نسخه فعلی قدیمی باشد، ابزار هشدار می‌دهد؛ مسیر پله‌پله را طی کنید و بین هر پله `hsctl status` را ببینید. نصب نسخه مشخص: `sudo hsctl update --version X.Y.Z`

اگر وسط کار مشکلی پیش آمد: اول `hsctl doctor`، بعد در بدترین حالت `hsctl restore` با آخرین پشتیبان سالم (فصل نهم).

## کار با پیکربندی

سه دستور برای فایل پیکربندی سرور:

```bash
hsctl config path         # مسیر فایل: /etc/headscale/config.yaml
hsctl config validate     # آیا فایل سالم و قابل‌فهم است؟
hsctl config show         # نمایش پیکربندی نهایی مؤثر
```

**قاعده طلایی ویرایش:** هر بار که فایل را دستی ویرایش کردید: ۱) ویرایش، ۲) `hsctl config validate` (اگر خطا گفت، اصلاح و دوباره)، ۳) `sudo systemctl restart headscale`، ۴) `hsctl status`. هرگز بدون `validate` ری‌استارت نکنید — همین یک عادت، جلوی بیشترِ قطعی‌ها را می‌گیرد.

## مدیریت از رابط گرافیکی (برنامهٔ ویندوزی)

برنامهٔ ویندوزی همین کارها را با کلیک انجام می‌دهد — اما هیچ جادویی در کار نیست: پشت هر دکمه، **دستور واقعی همین مخزن** روی سرور اجرا می‌شود. جدول زیر نگاشت هر بخش رابط به همان دستورهاست (جزییات فلگ‌ها در FACTS §۴ مخزن):

| بخش رابط | دستور واقعی که اجرا می‌شود |
|---|---|
| داشبورد (آمار) | `headscale users list -o json` + `nodes list -o json` + `preauthkeys list -o json` + `version` |
| کاربران (`#/users`) | `users list -o json` / `users create <NAME>` / `users rename --identifier <ID> --new-name <NAME>` / `users destroy --identifier <ID> --force` (حذف با تأیید تایپی) |
| دستگاه‌ها (`#/nodes`) | `nodes list -o json` / `nodes expire --identifier <ID> [--disable]` / `nodes rename` / `nodes tag` / `nodes delete --identifier <ID> --force` |
| کلیدها (`#/keys`) | PreAuth: `preauthkeys create -u <USER_ID> [--reusable] [--ephemeral] [-e] [--tags]` (کلید کامل فقط یک‌بار) + `list` ماسک‌شده + `expire --id` / `delete --id` · API: `apikeys create` / `list` / `expire --prefix` |
| مسیرها (`#/routes`) | `nodes list-routes -o json` + `nodes approve-routes --identifier <ID> --routes <CIDR,...>` (رشتهٔ خالی = لغو همه؛ جفت Exit Node خودکار) |
| سیاست (`#/policy`) | `policy get -o json` (ناموجود → «بدون سیاست») / `policy check` (اعتبارسنجی) / `policy set -f <فایل>` فقط در `policy.mode=database` |
| پیکربندی (`#/config`) | خواندن `config.yaml` + `configtest` (اعتبارسنجی) + اعمال = پشتیبان، نوشتن، `configtest`، ری‌استارت و سلامت مجدد؛ در شکست، بازگردانی خودکار |
| سرور و لاگ (`#/server`) | `systemctl is-active/is-enabled/status` + `journalctl -u` + `ss -tulpn` + `df -h` + `curl` محلیِ `/health` + `headscale health` (سه‌لایه) |
| پشتیبان و ارتقا (`#/backup`) | `hsctl backup create/list/verify` + `hsctl restore <FILE>` (با پشتیبان پیش از بازیابی) + `hsctl update --check` / `hsctl update --yes` |
| نصب سرور (`#/install`) | آپلود مخزن به سرور + `bash install.sh --dry-run --config answers.conf --non-interactive` و سپس اجرای واقعی با sudo/رضایت صریح |
| کنسول (`#/console`) | فقط دستورهای مجاز فهرست‌شده (پیش‌نمایش = عین فرمان اجرا) — بدون شل آزاد |

سه قاعدهٔ صادقانه که در رابط هم دقیقاً رعایت می‌شود:

- عملیات مخرب (حذف کاربر/دستگاه، بازیابی، توقف سرویس، اعمال سیاست/پیکربندی) **قبل از اجرا تأیید صریح** با نام واقعی همان شیء می‌گیرد؛
- مقدار کامل کلید PreAuth/API فقط **یک‌بار** نمایش داده می‌شود؛ بعدش فقط ماسک؛
- اگر `hsctl` روی سرور نصب نباشد (سروری که با این ابزار نصب نشده)، بخش پشتیبان/ارتقا به‌جای دادهٔ ساختگی، کارت صادقانهٔ «پس از نصب در دسترس» نشان می‌دهد.

راهنمای کامل برنامهٔ ویندوزی (اجرای آن، اتصال، اثر انگشت، ذخیرهٔ امن، عیب‌یابی): [فصل پانزدهم](15-barnameh-windows.md).

## دوربین‌های مداربسته در یک نگاه

ابزار یک بخش اختصاصی برای ثبت و بررسی دستگاه ضبط دوربین (NVR) دارد — آموزش کامل در **فصل سیزدهم**:

```bash
sudo hsctl cameras add                    # ثبت دستگاه جدید (پرسش‌های مرحله‌ای)
hsctl cameras list                        # لیست دستگاه‌های ثبت‌شده
hsctl cameras check --name nvr-daftar     # بررسی اتصال از نظر شبکه
sudo hsctl cameras remove nvr-daftar      # حذف دستگاه از لیست
```

نکته همین‌جا بگوییم: `hsctl` **هیچ رمز یا کلیدی از دوربین نمی‌پرسد و نگه نمی‌دارد**؛ فقط آدرس شبکه دستگاه را ثبت می‌کند تا «در دسترس بودن» را بررسی کند.

## گزارش قابل‌ارسال: `hsctl report`

وقتی می‌خواهید از همکار مسلط‌تری یا پشتیبانی کمک بگیرید، این دستور گزارشی کامل می‌سازد و **خودکار اطلاعات حساس (کلیدها و رمزها) را حذف می‌کند** تا با خیال راحت ارسالش کنید. مسیر خروجی هم می‌توانید مشخص کنید:

```bash
sudo hsctl report
sudo hsctl report --output <FILE>
```

```text
گزارش سیستم ساخته شد: hem-report-2025-01-15-110200.txt
اطلاعات حساس به‌صورت خودکار حذف/پوشانده شده‌اند.
```

قبل از ارسال، فایل را یک نگاه بیندازید که خیالتان راحت باشد — عادت خوبی است.

> 🧹 **و اگر روزی خواستید همه‌چیز را برچینید:** `sudo hsctl uninstall` ابزار را از سرور برمی‌دارد؛ با `--purge-data` داده‌ها هم کامل پاک می‌شوند — پیش از آن حتماً پشتیبان بگیرید و نسخه‌ای خارج از سرور نگه دارید.

## سناریوی ۱: حذف دستگاه ازدست‌رفته

لپ‌تاپ یکی از همکاران (مثلاً `laptop-reza` با ID 2) گم یا دزدیده شده است. به این ترتیب عمل کنید:

1. **پیدا کردن دستگاه:** `hsctl devices list` (شماره ID و آخرین وضعیت را ببینید)
2. **حذف فوری از شبکه** — تا هیچ‌کس نتواند با آن دوباره وصل شود:

```bash
sudo hsctl devices delete 2
```

3. **بازبینی کلیدهای همان کاربر:** `hsctl preauth list reza` — اگر کلیدِ فعالِ قابل‌استفاده‌مجدد دیدید، با دستور پایه موتور Headscale آن را منقضی کنید (شناسه از همان لیست):

```bash
sudo headscale preauthkeys expire --id 7
```

از این به بعد فقط کلید کوتاه‌عمر بسازید: `sudo hsctl preauth create reza --expiration 1h`

4. **تغییر رمز سرویس‌ها:** رمز CRM، دستگاه ضبط دوربین و هر سرویس دیگری که از آن لپ‌تاپ قابل دسترسی بود را عوض کنید — حذف از تونل، رمزهای ذخیره‌شده در مرورگرِ دستگاهِ گم‌شده را پاک نمی‌کند (جزئیات: فصل دهم).

## سناریوی ۲: تغییر دامنه یا گواهی سرور

گاهی لازم می‌شود دامنه عوض شود. این کار حساس است اما با رعایت ترتیب ممکن است. فرض: دامنه فعلی `headscale.example.com` و دامنه جدید `vpn.example.com`.

> ⚠️ **صادقانه:** با تغییر دامنه، همه کلاینت‌ها باید دوباره با آدرس جدید ثبت شوند. بدون دلیلی قوی، دامنه را عوض نکنید.

1. **اول رکورد دامنه:** رکورد A دامنه جدید را به IP همین سرور اشاره دهید و با `nslookup vpn.example.com` تأیید کنید.
2. **ویرایش پیکربندی** در `/etc/headscale/config.yaml`:
   - `server_url: https://vpn.example.com`
   - `dns.base_domain` به یک زیردامنه **متفاوت** (مثلاً `ts.example.com`) — این دو مقدار نباید یکی باشند.
3. **ویرایش بلوک Caddy** در `/etc/caddy/Caddyfile` — فقط بلوک بین مارکرهای `# BEGIN headscale-easy-manager` و `# END headscale-easy-manager` (نام دامنه قدیمی را به جدید تغییر دهید).
4. **اعتبارسنجی هر دو، قبل از اجرا:**

```bash
hsctl config validate
caddy validate --config /etc/caddy/Caddyfile
```

5. **اعمال و تست:**

```bash
sudo systemctl restart headscale
sudo systemctl reload caddy
```

سپس در مرورگر `https://vpn.example.com/health` را باز کنید — پاسخ سالم بگیرید، نه خطای گواهی و نه خطای اتصال. گواهی TLS جدید خودکار توسط Caddy از Let's Encrypt گرفته می‌شود.

6. **اتصال مجدد کلاینت‌ها** — روی هر دستگاه دوباره: `sudo tailscale up --login-server https://vpn.example.com` و در گوشی‌ها، آدرس سرور را در تنظیمات اپ Tailscale عوض کنید (روش دقیق: فصل پنجم).

## سناریوی ۳: انتقال کامل سرویس به VPS جدید

مثلاً می‌خواهید به ارائه‌دهنده سرور مجازی جدید بروید. با پشتیبان و بازیابی، **همه چیز** (کاربران، دستگاه‌ها، کلیدها و تنظیمات) منتقل می‌شود.

> 💡 کلید موفقیت: **تا آخرین لحظه رکورد دامنه را عوض نکنید** تا قطعی کوتاه باشد.

1. **روی سرور قدیم — پشتیبان کامل:** `sudo hsctl backup create` (مثلاً `/var/backups/hem/hem-backup-20250116-090000.tar.gz` ساخته می‌شود)
2. **انتقال امن فایل به سرور جدید** با `scp` (انتقال رمزنگاری‌شده):

```bash
scp /var/backups/hem/hem-backup-20250116-090000.tar.gz <USER>@<IP-سرور-جدید>:/tmp/
```

3. **نصب تازه روی سرور جدید** (طبق فصل چهارم؛ دامنه را **همان دامنه قبلی** وارد کنید):

```bash
sudo ./install.sh
```

از حالت خودکار هم می‌توانید استفاده کنید: فایل نمونه `examples/hem-install.conf.example` را مطابق شرایط خود پر کنید (حتماً با دسترسی ۶۰۰) و `sudo ./install.sh --config hem-install.conf --non-interactive` را اجرا کنید.

4. **بازیابی پشتیبان روی سرور جدید:**

```bash
sudo hsctl restore hem-backup-20250116-090000.tar.gz
```

5. **تغییر رکورد A دامنه** در پنل دامنه به IP سرور **جدید**.
6. **تست سلامت:**

```bash
curl -s -o /dev/null -w "%{http_code}\n" https://headscale.example.com/health
hsctl status
hsctl doctor
```

کد `200` یعنی سرور جدید از پشت دامنه سالم پاسخ می‌دهد.

7. **تست کلاینت‌ها:** روی یک لپ‌تاپ `tailscale status` بگیرید، با گوشی یک‌بار VPN را قطع/وصل کنید تا به سرور جدید وصل شود، و بین دو دستگاه `tailscale ping` بزنید.

> 🔎 **صادقانه — چه چیزی تغییر می‌کند:**
> - با حفظ دامنه (روش بالا)، کلاینت‌ها معمولاً بدون هیچ کاری وصل می‌شوند؛ فقط تا پخش‌شدن رکورد DNS یک قطعی کوتاه دارید.
> - اگر دامنه را هم عوض کنید، همه کلاینت‌ها باید دوباره `--login-server` بدهند و ثبت شوند.
> - چون پایگاه‌داده و کلیدها منتقل شده‌اند، کاربران و دستگاه‌ها **دقیقاً با همان شناسه‌ها** برمی‌گردند.
> - سرور قدیم را چند روز خاموش نگه دارید (نه حذف!) تا اگر چیزی جا مانده بود، قابل بازیابی باشد.

## خلاصه فصل

- `hsctl status` وضعیت کلی، `hsctl doctor` چکاپ چهاربخشی (مشکل/علت/بررسی/راهکار)، `hsctl logs` دفترچه رخدادها.
- کاربر: `users create/list/delete` — دستگاه: `devices list/delete` (تأیید قبل از حذف را جدی بگیرید).
- کلید از پیش تأییدشده فقط **یک‌بار** نمایش داده می‌شود؛ کوتاه‌عمر بسازید و امن منتقل کنید.
- مسیر شبکه دفتر: `routes approve` برای فعال‌سازی، `routes revoke` برای بستن.
- پشتیبان (`backup create` + `backup verify`) و بازیابی (`restore`) بعد از هر تغییر مهم.
- به‌روزرسانی در پنج مرحله امن و **نسخه‌به‌نسخه**؛ اول همیشه `update --check`.
- بعد از هر ویرایش پیکربندی، قبل از ری‌استارت: `hsctl config validate`.
- از برنامهٔ ویندوزی هم همهٔ همین کارها قابل انجام است؛ هر دکمه همان دستور واقعی را روی سرور اجرا می‌کند (جدول نگاشت در همین فصل).
- دستگاه ازدست‌رفته: حذف → رسیدگی به کلیدها → تغییر رمز سرویس‌ها.
- انتقال به سرور جدید: پشتیبان → scp → نصب تازه → restore → تغییر رکورد A → تست سلامت و کلاینت‌ها.
