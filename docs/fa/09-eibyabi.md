## در این فصل یاد می‌گیرید

- یک روش فکری مرتب برای عیب‌یابی: **الگوی چهار سؤالی**
- مشکلات را در **شش لایه** (از DNS تا اپلیکیشن) دسته‌بندی و جدا کنید
- همیشه اول `hsctl doctor` — و بدانید چه چیزی به شما می‌گوید
- لاگ‌ها را مثل یک متخصص بخوانید (`hsctl logs` و `journalctl`)
- **۱۴ خطای رایج** را با نشانه، دستور بررسی، معنی خروجی، علت احتمالی و راهکار ایمن رفع کنید

وقتی چیزی کار نمی‌کند، اولین احساس نگرانی طبیعی است؛ اما خبر خوب این است که تقریباً همه مشکلات شبکه از یک مجموعه **معلوم و شناخته‌شده** هستند. این فصل، جعبه‌ابزار شما برای روزهای بد است.

## قانون اول: همیشه اول `hsctl doctor`

قبل از هر حدس و گمانی، روی سرور اجرا کنید:

```bash
hsctl doctor
```

این دستور ده‌ها بررسی خودکار انجام می‌دهد و برای هر مشکل، خروجی را در چهار بخش می‌دهد: **مشکل / علت احتمالی / چگونه بررسی شد / راهکار**. بسیاری از مواقع، همان راهکار پیشنهادی، مشکل را حل می‌کند و لازم نیست اصلاً ادامه این فصل را بخوانید!

```text
✖ مشکل: سرویس headscale اجرا نمی‌شود
   علت احتمالی: توقف غیرمنتظره سرویس یا خطا در فایل پیکربندی
   چگونه بررسی شد: systemctl is-active headscale → پاسخ «inactive»
   راهکار: sudo systemctl start headscale
```

اگر `doctor` مشکل را رفع‌کردنی دانست، می‌توانید بگذارید خودش امتحان کند: `hsctl doctor --fix`

## الگوی چهار سؤالی

وقتی `doctor` جواب نداد (یا مشکل سمت کلاینت/دفتر بود)، این چهار سؤال را به‌ترتیب از خودتان بپرسید:

1. **چه انتظاری داشتم؟** — دقیق و مشخص بگویید: «باید صفحه CRM در آدرس `http://192.168.1.220:800` در گوشی باز می‌شد.»
2. **چه چیزی دیدم؟** — دقیق و بدون تعبیر: «مرورگر نوشت اتصال برقرار نشد و بعد از مدت زیادی تایم‌اوت شد.»
3. **چه چیزی بین این دو فاصله ایجاد کرده؟** — مسیر را روی کاغذ بیاورید: گوشی → تونل VPN → ساب‌نت‌روتر دفتر → شبکه دفتر → CRM. هرکدام از این‌ها می‌تواند مقصر باشد.
4. **مشکل در کدام لایه است؟** — با نقشه زیر، لایه‌ها را از نزدیک به دور تست کنید تا لایه خراب پیدا شود.

## نقشه شش لایه

| لایه | چه چیزی را بررسی می‌کند | چگونه تست کنیم |
|---|---|---|
| ۱. DNS | آیا دامنه به IP درست اشاره می‌کند؟ | `nslookup <دامنه>` |
| ۲. TLS/HTTPS | آیا وب‌سرور و گواهی سالم‌اند؟ | باز کردن `https://<دامنه>/health` در مرورگر |
| ۳. سرویس | آیا Headscale اصلاً اجرا می‌شود؟ | `hsctl status` و `sudo systemctl status headscale` |
| ۴. تونل | آیا کلاینت‌ها به سرور وصل‌اند؟ | `tailscale status` و `tailscale ping` |
| ۵. مسیر (Route) | آیا ترافیک به شبکه دفتر می‌رسد؟ | `hsctl routes list` و پینگ IP دفتر |
| ۶. اپلیکیشن | آیا خود CRM/NVR جواب می‌دهد؟ | باز کردن آدرس CRM در مرورگر (از داخل دفتر و از تونل) |

**روش کار:** از لایه ۱ شروع کنید و به پایین بیایید. اولین لایه‌ای که خراب بود، همان‌جا باید تعمیر کنید — تعمیر لایه‌های سالم فقط وقت‌تان را تلف می‌کند.

## جدول سریع: خطا، و اولین دستور بررسی

| # | مشکل | اولین دستور بررسی |
|---|---|---|
| ۱ | دامنه به IP اشتباه اشاره می‌کند | `hsctl doctor` یا `nslookup <دامنه>` |
| ۲ | HTTPS برقرار نمی‌شود | `sudo journalctl -u caddy -n 50 --no-pager` |
| ۳ | سرویس Headscale اجرا نمی‌شود | `sudo systemctl status headscale` |
| ۴ | کلاینت به سرور وصل نمی‌شود | `tailscale status` |
| ۵ | دستگاه ثبت نمی‌شود | `hsctl preauth list <USER>` |
| ۶ | دستگاه‌ها یکدیگر را نمی‌بینند | `tailscale ping <IP-یا-نام>` |
| ۷ | IP تونل جواب می‌دهد ولی CRM نه | `hsctl routes list` |
| ۸ | مسیر (Route) شبکه دفتر فعال نیست | `hsctl routes list` |
| ۹ | فایروال مسیر را بسته | `sudo ufw status` |
| ۱۰ | مسیر برگشت ترافیک مشکل دارد | بررسی گیت‌وی پیش‌فرض روتر دفتر |
| ۱۱ | سرویس بعد از ری‌استارت بالا نمی‌آید | `hsctl config validate` |
| ۱۲ | فضای دیسک تمام شده | `df -h` |
| ۱۳ | به‌روزرسانی ناموفق بوده | `hsctl update --check` |
| ۱۴ | زمان سیستم/گواهی TLS مشکل دارد | `timedatectl` |

حالا هرکدام را با جزئیات ببینیم.

## خطای ۱: دامنه به IP اشتباه اشاره می‌کند

- **نشانه:** هیچ کلاینتی نمی‌تواند به سرور وصل شود؛ در مرورگر، آدرس `https://<دامنه>` باز نمی‌شود؛ `doctor` درباره دامنه هشدار می‌دهد.
- **دستور بررسی:**

```bash
nslookup headscale.example.com
```

```text
Name:    headscale.example.com
Address: 203.0.113.10
```

(اگر `dig` روی سیستم‌تان نصب است، خلاصه‌تر: `dig +short headscale.example.com`)

- **معنی خروجی:** عددی که در `Address` می‌بینید باید **دقیقاً IP عمومی سرور** باشد (همان IP که در پنل ارائه‌دهنده سرور مجازی نوشته شده). اگر عدد دیگری بود — یا پاسخی نیامد — دامنه به جای اشتباهی اشاره می‌کند.
- **علت احتمالی:** رکورد A ثبت نشده یا اشتباه وارد شده؛ دامنه تازه ثبت شده و هنوز پخش نشده؛ حالت «پروکسی» (مثل ابر ابری Cloudflare) روی دامنه فعال است — این حالت با Headscale سازگار **نیست** و باید خاموش شود.
- **راهکار ایمن:** در پنل دامنه، رکورد A دامنه را به IP عمومی سرور تغییر دهید و چند دقیقه صبر کنید. سپس دوباره `nslookup` بزنید و بعد `hsctl doctor` را ببینید. قبل از درست‌شدن DNS، هیچ کار دیگری جواب نمی‌دهد؛ عجله نکنید.

## خطای ۲: HTTPS برقرار نمی‌شود

- **نشانه:** مرورگر هنگام باز کردن `https://<دامنه>` خطای گواهی یا «اتصال امن برقرار نشد» می‌دهد؛ کلاینت‌ها هنگام اتصال خطای TLS می‌بینند.
- **دستور بررسی:** گواهی و HTTPS را نرم‌افزار Caddy مدیریت می‌کند؛ لاگ آن را ببینید:

```bash
sudo journalctl -u caddy -n 50 --no-pager
```

```text
… ERR [] obtain error … will retry …
… ERR [] challenge failed … dns problem …
```

- **معنی خروجی:** دنبال کلمه `ERR` بگردید. اگر درباره «challenge» یا «dns» است، یعنی صدور گواهی Let's Encrypt به خاطر دامنه/پورت‌ها شکست خورده است.
- **علت احتمالی:** رکورد دامنه هنوز به این سرور اشاره نمی‌کند (خطای ۱)؛ پورت 80 یا 443 در فایروال بسته است؛ دامنه قبلاً روی سرور دیگری بوده و گواهی جدید نیازمند انتشار DNS است.
- **راهکار ایمن:** اول خطای ۱ را حل کنید. بعد فایروال را ببینید:

```bash
sudo ufw status
```

اگر 80 و 443 در لیست مجاز نیستند، طبق فصل چهارم اجازه عبور بدهید. در نهایت Caddy را ری‌استارت کنید تا دوباره برای گواهی تلاش کند:

```bash
sudo systemctl restart caddy
```

و چند دقیقه بعد، آدرس `https://<دامنه>/health` را در مرورگر امتحان کنید.

## خطای ۳: سرویس Headscale اجرا نمی‌شود

- **نشانه:** `hsctl status` نشان می‌دهد سرویس فعال نیست؛ کلاینت‌های تازه نمی‌توانند وصل شوند.
- **دستور بررسی (سه‌تایی):**

```bash
sudo systemctl status headscale
sudo journalctl -u headscale -n 50 --no-pager
hsctl config validate
```

```text
● headscale.service - headscale controller
   Active: failed (Result: exit-code) since …
…
headscale[…]: FATA … error reading config … invalid configuration
```

- **معنی خروجی:** خط `Active: failed` یعنی سرویس کرش کرده؛ خطوط لاگ زیرش **دلیل** را می‌گویند. اگر درباره پیکربندی است، `config validate` هم خطا می‌دهد.
- **علت احتمالی:** ویرایش دستی `/etc/headscale/config.yaml` با یک تایپ یا فرمت اشتباه (رایج‌ترین علت!)؛ پرشدن دیسک (خطای ۱۲)؛ مشکل فایل پایگاه‌داده.
- **راهکار ایمن:** اگر `config validate` خطا داد، فایل را اصلاح کنید، دوباره اعتبارسنجی کنید و بعد اجرا:

```bash
hsctl config validate
sudo systemctl start headscale
hsctl status
```

اگر خطا درباره دیسک یا پایگاه‌داده بود، به خطای ۱۲ بروید.

## خطای ۴: کلاینت به سرور وصل نمی‌شود

- **نشانه:** روی گوشی/لپ‌تاپ، اپلیکیشن یا `tailscale status` می‌گوید اتصال برقرار نیست؛ گاهی با خطای «login server».
- **دستور بررسی (روی همان کلاینت):**

```bash
tailscale status
```

```text
Logged out.
```

- **معنی خروجی:** `Logged out` یعنی اصلاً به هیچ سروری وصل نیست. اگر `tailscale status` دستگاه‌ها را نشان می‌دهد ولی کار نمی‌کنند، مشکل شما خطای ۶ یا ۷ است.
- **علت احتمالی:**
  - آدرس سرور غلط تایپ شده (بدون `https://` یا با دامنه اشتباه)؛
  - اینترنتِ خود دستگاه قطع است؛
  - شبکه‌ای که کلاینت در آن است، خروجی پورت 443 را می‌بندد (مثلاً وای‌فای شرکت دیگر)؛
  - سرور واقعاً خاموش است (خطای ۳) یا دامنه خراب است (خطای ۱).
- **راهکار ایمن:** به‌ترتیب: ۱) در مرورگر همان دستگاه آدرس `https://<دامنه>/health` را باز کنید — اگر باز شد، سرور و DNS و HTTPS سالم‌اند و مشکل از تنظیم کلاینت است؛ ۲) آدرس سرور را دقیق چک کنید:

```bash
sudo tailscale up --login-server https://headscale.example.com
```

۳) اگر صفحه سلامت باز نشد، مشکل سمت سرور است؛ به خطاهای ۱ تا ۳ برگردید.

## خطای ۵: دستگاه ثبت نمی‌شود

- **نشانه:** دستور `tailscale up` را زده‌اید (یا در اپلیکیشن کلید را وارد کرده‌اید) ولی دستگاه در `hsctl devices list` ظاهر نمی‌شود.
- **دستور بررسی:**

```bash
hsctl devices list
hsctl preauth list admin
```

```text
ID   اعتبار   قابل استفاده مجدد   وضعیت
5    1h        خیر                منقضی‌شده
```

- **معنی خروجی:** اگر وضعیت کلید «منقضی‌شده» یا «مصرف‌شده» است، دستگاه با آن کلید ثبت نشده و در لیست دستگاه‌ها هم نمی‌آید.
- **علت احتمالی:**
  - کلید از پیش تأییدشده **منقضی شده** (انقضای پیش‌فرض فقط ۱ ساعت است!)؛
  - کلید یک‌بارمصرف بوده و قبلاً یک دستگاه دیگر آن را مصرف کرده؛
  - اگر بدون کلید و به‌صورت تعاملی وصل شده‌اید، جریان تأیید روی سرور کامل نشده است.
- **راهکار ایمن:** ساده‌ترین راه، کلید تازه است:

```bash
sudo hsctl preauth create admin --expiration 1h
```

و روی دستگاه:

```bash
sudo tailscale up --login-server https://headscale.example.com --authkey <AUTH_KEY>
```

اگر با روش مرورگری (تعاملی) وصل می‌شوید، سرور برای هر اتصال جدید یک شناسه احراز هویت (Auth ID) تولید می‌کند که باید روی سرور تأیید شود — دستور پایه موتور Headscale برای آن چنین است و در فصل پنجم توضیح داده شده:

```bash
sudo headscale auth register --user admin --auth-id <AUTH_ID>
```

## خطای ۶: دستگاه‌ها یکدیگر را نمی‌بینند

- **نشانه:** دو دستگاه هر دو «وصل» به نظر می‌رسند ولی پینگ و اتصال بین‌شان کار نمی‌کند.
- **دستور بررسی (روی یکی از دستگاه‌ها):**

```bash
tailscale ping laptop-reza
```

```text
pong from laptop-reza (100.64.0.2) via DERP(headscale) in 120ms
```

- **معنی خروجی:** اگر `pong` گرفتید یعنی تونل بین این دو دستگاه سالم است و مشکل از لایه‌های دیگر است (مثلاً خطای ۷). اگر `timeout` گرفتید، این دو دستگاه واقعاً یکدیگر را نمی‌بینند.
- **علت احتمالی:** یکی از دو دستگاه به سرور دیگری (مثلاً سرور عمومی Tailscale به‌جای سرور شما) وصل است؛ یا فایل سیاست (Policy) محدودکننده‌ای روی سرور تنظیم شده — در نصب پیش‌فرض این ابزار فایل سیاست خالی است و همه دستگاه‌های یک شبکه آزادند یکدیگر را ببینند، پس اگر سیاستی نساخته‌اید این علت منتفی است.
- **راهکار ایمن:** روی هر دو دستگاه `tailscale status` بگیرید و مطمئن شوید هر دو به **یک سرور** وصل‌اند؛ در صورت تردید، روی هر دو آدرس سرور را یکسان اجرا کنید:

```bash
sudo tailscale up --login-server https://headscale.example.com
```

اگر فایل سیاست تنظیم کرده‌اید، مجوزهایش را بازبینی کنید (مفهوم سیاست در فصل سوم و دهم).

## خطای ۷: IP تونل جواب می‌دهد ولی CRM در دسترس نیست

- **نشانه:** `tailscale ping` به دستگاه دفتر جواب می‌دهد (تونل سالم!) ولی وقتی `http://192.168.1.220:800` را باز می‌کنید، صفحه نمی‌آید.
- **دستور بررسی:** لایه‌ها را جدا کنید — اول مسیر، بعد خود CRM:

```bash
hsctl routes list
```

```text
ID   دستگاه          موجود (Advertised)   تأییدشده (Approved)   فعال
1    office-router   192.168.1.0/24       —                    —
```

- **معنی خروجی:** مسیر «موجود» است ولی «تأییدنشده»! یعنی دستگاه دفتر جاده را پیشنهاد داده ولی سرور هنوز آن را باز نکرده — تا این شود، هیچ کلاینتی به 192.168.1.220 نمی‌رسد.
- **علت احتمالی:** تأیید مسیر فراموش شده (خطای ۸)؛ کلاینت لینوکسی مسیرها را نمی‌پذیرد (`accept-routes` فعال نیست)؛ فایروال دفتر ترافیک تونل را می‌بندد (خطای ۹)؛ یا خود CRM از داخل دفتر هم بالاخره پایین است!
- **راهکار ایمن:** چهار قدم به‌ترتیب:
  1. تأیید مسیر: `sudo hsctl routes approve 1 --routes 192.168.1.0/24`
  2. روی کلاینت لینوکسی: `sudo tailscale set --accept-routes` (ویندوز و اندروید خودکار می‌پذیرند)
  3. از داخل دفتر (یک کامپیوتر معمولی دفتر) آدرس CRM را باز کنید — اگر آنجا هم باز نشد، مشکل از خود CRM است، نه VPN ما.
  4. اگر فقط از تونل باز نمی‌شود، بروید سراغ خطای ۹ و ۱۰.

## خطای ۸: مسیر (Route) شبکه دفتر فعال نیست

- **نشانه:** ستون «تأییدشده» در لیست مسیرها خالی است؛ یا اصلاً مسیری «موجود» نیست.
- **دستور بررسی:**

```bash
hsctl routes list
```

- **معنی خروجی:**
  - سطر با «موجود» ولی بدون «تأییدشده» → فقط باید تأیید کنید: `sudo hsctl routes approve <ID> --routes 192.168.1.0/24`
  - **هیچ سطری نیست** → دستگاه دفتر اصلاً مسیرش را پیشنهاد نمی‌کند؛ روی دستگاه دفتر اجرا کنید:

```bash
sudo tailscale set --advertise-routes=192.168.1.0/24
```

  و مطمئن شوید «IP فورواردینگ» روی همان دستگاه فعال است (فصل ششم).
- **علت احتمالی:** فراموشی تأیید بعد از نصب؛ ری‌استارت/نصب مجدد tailscale روی دستگاه دفتر بدون فلگ advertise؛ تغییر IP شبکه دفتر.
- **راهکار ایمن:** بعد از هر تغییر، دوباره `hsctl routes list` بگیرید تا ستون «تأییدشده» و «فعال» پر شود. برای لغو کامل مسیرهای یک دستگاه هم `sudo hsctl routes revoke <ID>` هست — اما استفاده‌اش فقط وقتی واقعاً می‌خواهید جاده را ببندید.

## خطای ۹: فایروال مسیر را بسته است

- **نشانه:** تونل سالم است، مسیر تأیید شده، ولی باز هم به هیچ دستگاهی از دفتر نمی‌رسید.
- **دستور بررسی (روی سرور):**

```bash
sudo ufw status
```

```text
Status: active
To                         Action      From
--                         ------      ----
22/tcp                     ALLOW       Anywhere
80/tcp                     ALLOW       Anywhere
443/tcp                    ALLOW       Anywhere
3478/udp                   ALLOW       Anywhere
```

- **معنی خروجی:** این لیست برای **سرور** درست است (پورت‌های 22، 80، 443 و 3478/udp). اما وقتی مشکل «رسیدن به شبکه دفتر» است، مظنون اصلی فایروالِ **سمت دفتر** است: روتر/مودم دفتر یا فایروال روی خود دستگاه‌ها، ترافیکِ رسیده از تونل را (که با IPهایی از رنج `100.64.0.0/10` می‌آید) دور می‌ریزد.
- **علت احتمالی:** فایروال روتر دفتر ترافیک «ناشناخته» از رنج 100.x را بلاک می‌کند؛ آنتی‌فایروال ویندوزیِ دستگاه مقصد (مثل سرور CRM) پینگ و پورت‌ها را می‌بندد.
- **راهکار ایمن:** در فایروالِ سمت دفتر، عبور ترافیک از رنج `100.64.0.0/10` به سمت شبکه دفتر را مجاز کنید (هر روتر رابط مدیریتی متفاوتی دارد — دفترچه یا پشتیبانی سازنده روتر کمک می‌کند). اگر مقصدِ شما سروری با ویندوز است، در فایروال ویندوزِ آن، اجازه‌ی پورت CRM داده شود. تغییرات را یکی‌یکی و با تست بعد از هر تغییر انجام دهید.

## خطای ۱۰: مسیر برگشت ترافیک مشکل دارد

- **نشانه:** همه‌چیز درست به نظر می‌رسد ولی پاسخِ درخواست‌ها هرگز برنمی‌گردد (مثلاً پینگ به `192.168.1.220` تایم‌اوت می‌شود در حالی که از `tailscale ping` به ساب‌نت‌روتر جواب می‌گیرید).
- **چه اتفاقی می‌افتد؟** درخواست شما با IP تونل (مثلاً `100.64.0.2`) وارد شبکه دفتر می‌شود. دستگاه CRM برای جواب‌دادن، باید پاسخ را به `100.64.0.2` بفرستد — اما از کجا بداند این آدرس کجاست؟ پاسخ را به **گیت‌وی پیش‌فرض** (روتر اصلی دفتر) می‌دهد؛ اگر روتر اصلی نداند که رنج `100.64.0.0/10` نزد ساب‌نت‌روتر است، جواب را به سمت اینترنت می‌فرستد و جواب برای همیشه گم می‌شود!
- **دستور بررسی:** این یکی از معدود مواردی است که با دستور سرور حل نمی‌شود — باید وارد تنظیمات **روتر اصلی دفتر** شوید و ببینید: آیا کامپیوترِ ساب‌نت‌روتر، خودش گیت‌وی پیش‌فرض شبکه است؟ (آنگاه همه‌چیز خودکار درست است) — و اگر نه، آیا مسیری برای `100.64.0.0/10` به سمت IP محلی ساب‌نت‌روتر تعریف شده؟
- **راهکار ایمن:** در روتر دفتر یک **مسیر ایستا (Static Route)** اضافه کنید: مقصد `100.64.0.0/10`، گیت‌وی = IP محلی ساب‌نت‌روتر در شبکه دفتر (مثلاً `192.168.1.50`). بعد از ذخیره، از گوشی دوباره تست کنید. (نام دقیق این بخش در روترهای مختلف فرق دارد؛ معمولاً زیر «Routing» یا «Static Route» است.)

## خطای ۱۱: سرویس بعد از ری‌استارت بالا نمی‌آید

- **نشانه:** سرور را ری‌استارت کرده‌اید (یا برق رفته) و سرویس headscale دیگر بالا نمی‌آید؛ در حالی که قبلاً سالم بود.
- **دستور بررسی:**

```bash
sudo systemctl status headscale
hsctl config validate
sudo journalctl -u headscale -n 50 --no-pager
```

- **معنی خروجی:** تقریباً همیشه، `journalctl` خط اول دلیل را می‌گوید. رایج‌ترین حالت: `config validate` خطای فایل پیکربندی می‌دهد — یعنی قبلاً فایل را ویرایش کرده‌اید و چون تا قبل از ری‌استارت سرویسِ در حال اجرا دست‌نخورده بود، مشکل خودش را نشان نداده بود.
- **علت احتمالی:** ویرایش اشتباه پیکربندی (تایپ، فرمت YAML ناقص، فاصله‌های جابه‌جا)؛ کمبود فضا (خطای ۱۲).
- **راهکار ایمن:** فایل را اصلاح کنید تا `hsctl config validate` سبز شود، بعد:

```bash
sudo systemctl start headscale
hsctl status
```

قاعده برای آینده: بعد از **هر** ویرایش پیکربندی، همان لحظه `validate` و `restart` کنید — نه اینکه برای بعد بگذارید.

## خطای ۱۲: فضای دیسک تمام شده است

- **نشانه:** سرویس‌ها کرش می‌کنند، لاگ‌ها می‌ایستند، خطاهای عجیب نوشتن فایل می‌بینید؛ `hsctl status` هم ممکن است هشدار فضا بدهد.
- **دستور بررسی:**

```bash
df -h
```

```text
Filesystem      Size  Used Avail Use% Mounted on
/dev/vda1        25G   24G     0 100% /
```

- **معنی خروجی:** به ستون `Use%` پارتیشن اصلی (`/`) نگاه کنید. عدد بالای ۹۰٪ یعنی خطر؛ ۱۰۰٪ یعنی همه‌چیز می‌تواند از کار بیفتد.
- **علت احتمالی:** انباشت فایل‌های پشتیبان در `/var/backups/hem/`، بزرگ‌شدن لاگ‌ها، یا نصب‌های تکراری سیستم‌عامل.
- **راهکار ایمن:** با `hsctl backup list` ببینید چند پشتیبان دارید؛ نسخه‌های قدیمی را **بعد از کپی‌کردن به محل امن** (مثلاً کامپیوتر شخصی‌تان) از سرور حذف کنید تا چند نسخه اخیر بماند. اگر فضا همچنان کم است، از پنل ارائه‌دهنده، دیسک سرور مجازی را بزرگ‌کنید. هرگز فایل‌های `/var/lib/headscale/` یا `/etc/headscale/` را برای «خالی‌کردن فضا» پاک نکنید — این‌ها مغز شبکه شما هستند.

## خطای ۱۳: به‌روزرسانی ناموفق بوده است

- **نشانه:** بعد از `hsctl update`، سرویس بالا نمی‌آید یا نسخه‌ها ناسازگار به نظر می‌رسند.
- **دستور بررسی:**

```bash
hsctl update --check
hsctl logs --lines 100
```

- **معنی خروجی:** اگر `--check` تفاوت عجیبی بین نسخه نصب‌شده و انتظاری نشان می‌دهد، یا لاگ‌ها بعد از زمان به‌روزرسانی پر از خطا هستند، یعنی فرایند نیمه‌کاره مانده است.
- **علت احتمالی:** پرش از یک نسخه به چند نسخه بعد (به‌جای ارتقای نسخه‌به‌نسخه)؛ قطعی اینترنت وسط دانلود؛ کمبود فضا وسط نصب.
- **راهکار ایمن:** آرام باشید — دقیقاً برای همین لحظه پشتیبان گرفته شده بود. با آخرین پشتیبان سالم برگردید:

```bash
hsctl backup list
sudo hsctl restore <FILE>
hsctl status
```

بعد از برگشت به حالت پایدار، ارتقا را **پله‌پله** (مثلاً 0.27 → 0.28 → 0.29، بدون پرش) و با پشتیبان تازه قبل از هر پله دوباره انجام دهید (جزئیات در فصل هشتم).

## خطای ۱۴: زمان سیستم یا گواهی TLS مشکل دارد

- **نشانه:** خطاهای عجیب گواهی در مرورگرها؛ Caddy در لاگ‌هاش از Let's Encrypt خطا می‌گیرد؛ یا سرور زمان اشتباهی نشان می‌دهد.
- **دستور بررسی:**

```bash
timedatectl
```

```text
               Local time: Mon 2025-01-15 10:20:03 +0330
           Universal time: Mon 2025-01-15 06:50:03 UTC
                 Time zone: Asia/Tehran (UTC+0330)
System clock synchronized: yes
              NTP service: active
```

- **معنی خروجی:** `System clock synchronized` و `NTP service` باید هر دو فعال/بله باشند و تاریخ هم واقعی. اگر تاریخ سرور با واقعیت اختلاف زیاد دارد، صدور و اعتبارسنجی گواهی‌های TLS (که تاریخ‌محورند) به‌هم می‌ریزد و همه‌چیز «بدون دلیل واضح» خراب می‌شود.
- **علت احتمالی:** خاموش‌بودن همگام‌سازی زمان پس از ری‌استارت سرور یا نصب اولیه.
- **راهکار ایمن:** همگام‌سازی خودکار زمان و منطقه زمانی را فعال کنید:

```bash
sudo timedatectl set-ntp true
sudo timedatectl set-timezone Asia/Tehran
```

سپس چند دقیقه بعد، سلامت HTTPS را با `https://<دامنه>/health` و لاگ Caddy (`sudo journalctl -u caddy -n 50 --no-pager`) بررسی کنید.

## خواندن لاگ‌ها مثل یک متخصص

سه منبع رخداد دارید؛ هرکدام برای چیزی:

| منبع | دستور | برای چه؟ |
|---|---|---|
| لاگ یکپارچه ابزار | `hsctl logs --lines 100` | دیدن سریع رخدادهای سرویس Headscale |
| لاگ زنده | `hsctl logs --follow` | تماشای لحظه‌ای هنگام تست (خاموش‌کردن با Ctrl+C) |
| لاگ خود سیستم‌عامل | `sudo journalctl -u headscale -n 100 --no-pager` | وقتی خود سرویس بالا نیامده و hsctl چیزی نمی‌گوید |
| لاگ Caddy | `sudo journalctl -u caddy -n 100 --no-pager` | مشکلات HTTPS و گواهی |

سه عادت طلایی در خواندن لاگ:

1. **از پایین بخوانید به بالا** — جدیدترین رخداد آخر است و معمولاً همان خطای اصلی آنجاست.
2. **دنبال سه کلمه بگردید:** `ERR` (خطا — جدی)، `WRN` (هشدار — ببینیدش)، `INF` (اطلاعات — عادی).
3. **تایم‌استمپ‌ها را با زمان مشکل تطبیق دهید** — خطای سه روز پیش ربطی به قطعی امروز ندارد.

وقتی خواستید از کسی کمک بگیرید، به‌جای عکس‌برداری از همه‌چیز، از `sudo hsctl report` استفاده کنید که خودش اطلاعات حساس را حذف می‌کند (فصل هشتم).

## اگر هیچ‌کدام نشد؟

- `hsctl doctor` تمیز است ولی مشکل پابرجا؟ لایه‌ها را دوباره و با دقت تست کنید — بیش از حد معمول، مشکل ترکیبی است (مثلاً هم DNS هنوز در حال پخش است و هم کلید منقضی شده).
- آخرین پناهگاه امن، بازیابی از آخرین پشتیبان سالم است (`hsctl restore`) — و اگر سرور خودش در دسترس نیست، انتقال کامل به سرور جدید با همان پشتیبان (سناریوی ۳ فصل هشتم).
- از داستان‌های واقعی یاد بگیرید: در فصل دوازدهم، یک خطای عمدی می‌سازیم و با همین الگوی چهار سؤالی حلش می‌کنیم.

## خلاصه فصل

- **همیشه اول `hsctl doctor`** — چهار بخشِ خروجی‌اش (مشکل/علت/بررسی/راهکار) مسیر را نشان می‌دهد.
- با **الگوی چهار سؤالی** و **نقشه شش لایه** (DNS → TLS → سرویس → تونل → مسیر → اپلیکیشن) به‌جای حدس‌زدن، لایه خراب را پیدا کنید.
- ۱۴ خطای رایج را شناختید: از DNS و گواهی تا مسیر برگشت و فضای دیسک.
- برای هر خطا، اول **دستور بررسی**، بعد **معنی خروجی**، و در آخر **راهکار ایمن** — نه برعکس!
- لاگ‌ها دوست شما هستند: `hsctl logs` برای کار روزمره، `journalctl` برای روزهای سخت.
- در بحران، پشتیبان + `hsctl restore` همیشه آخرین راه نجات امن است.
