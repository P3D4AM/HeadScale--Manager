# گزارش تغییرات (Changelog)

## [0.3.2-beta.1] — ۲۰۲۶-۱۰-۲۵ — «سخت‌سازی امنیتی احراز هویت» (Pre-release از شاخهٔ develop)

> نسخهٔ توسعه (Beta) — از شاخهٔ `develop` منتشر شده و با نسخهٔ پایدار `main` اشتباه گرفته نشود. شامل تمام تغییرات [0.3.2] (رفع باگ UI ویندوزی) به‌علاوهٔ موارد زیر.

### رفع آسیب‌پذیری امنیتی: «عبور بدون احراز هویت در نبود توکن»
**مشکل:** middleware مربوط به `/api` در صورت نبودن `deps.token`، درخواست را بدون احراز هویت عبور می‌داد و WebSocket هم همین رفتار را داشت — یعنی «توکن تنظیم‌نشده» یعنی «سرویس کاملاً باز»؛ دقیقاً برعکسِ رفتار امن (fail-closed).

**مدل جدید (سه حالتِ صریح):**
- `token` (پیش‌فرض اجرای واقعی): توکن صریح `HEM_AGENT_TOKEN` یا (فقط دسکتاپ) تولید تصادفی امن `randomBytes(24)` برای همین اجرا. همهٔ `/api` (به‌جز health عمومیِ حداقلی) و همهٔ WebSocketها به هدر `X-HEM-Token` یا کوکی `hem_token` نیاز دارند (timing-safe؛ HTTP و WS هم‌ارز و سازگار).
- `open` (استثنای مستند و محدود توسعهٔ محلی): فقط با تنظیم صریح `HEM_AGENT_AUTH=open` و **فقط روی loopback** — روی هر آدرس شبکه‌ای راه‌اندازی با خطای روشن متوقف می‌شود (`HEM_AGENT_HOST` دیگر نمی‌تواند سرویسِ بی‌احراز هویتی روی شبکه بگذارد).
- **بدون توکن و بدون صراحت: شروع نمی‌شود** — پیام فارسی روشن `AUTH_NOT_CONFIGURED` + exit غیرصفر. لایهٔ API هم دفاعی 503 می‌دهد (defense-in-depth).
- ترکیب‌های متناقض همگی در شروع رد می‌شوند: `open`+توکن، `open`+دسکتاپ، `HEM_AGENT_AUTH=token` بدون توکن، مقدار نامعتبر.

**رفتار بایند:** پیش‌فرض `127.0.0.1`؛ بایند شبکه‌ای «با توکن» = انتخاب آگاهانه + هشدار صریح در لاگ؛ بایند شبکه‌ای «بدون احراز هویت» = توقف در شروع.

### مسیر عمومیِ صریح و محدود (Health Check)
`GET /api/health` تنها مسیر عمومی است: پاسخ حداقلی غیرحساس `{ok, service, version}` برای همه؛ فیلدهای تکمیلی (`uptimeSec, platform, sessions`) فقط برای درخواست احراز‌هویت‌شده. هیچ متد/مسیر دیگری عمومی نیست (`POST /api/health` و مسیرهای مشابه → 401/503).

### رفع نشت توکن در لاگ سرور (کشف‌شده توسط تست جدید)
هندلر «UI موجود نیست» قبلاً `req.originalUrl` را عیناً لاگ می‌کرد — لینک بوت‌استرپ بازیابی‌شده از تاریخچهٔ مرورگر (`GET /?token=…`) مقدار توکن را در لاگ سرور می‌نوشت. اکنون همهٔ URLهای لاگ‌شده از `Redactor` می‌گذرند (`token=***`). توکن دسکتاپ فقط در خط `desktop UI:` کنسول خود کاربر (کانال تحویل بوت‌استرپ) ظاهر می‌شود — نه در audit.log، نه در پاسخ‌های API، نه در هیچ خط لاگ دیگر (تست C7 همین را قفل می‌کند).

### تست‌های امنیتی واقعی (جدید — ۳۱ تست)
`test/security-auth.test.ts` هر ۷ سناریوی الزامی را در «سه لایهٔ مستقل» پوشش می‌دهد: (الف) سیاست خالص `resolveAuthPlan`/`isLoopbackHost` (۱۱)، (ب) رفتار HTTP/WS از طریق createApp/attachEvents در هر سه حالت (۱۳)، (ج) **فرایند واقعی** — spawn خودِ `bun index.ts`: رد شدنِ شروع در همهٔ ترکیب‌های ناامن/متناقض، هشدار بایند شبکه‌ای با توکن، و اجرای کامل دسکتاپ با توکن تولیدی + یک‌بارمصرف + اثبات عدم نشت (۷). تست‌های منطق کسب‌وکار موجود به استثنای مستند `open` منتقل شدند (بدون حذف/تضعیف هیچ تستی)؛ مجموع کل: **۱۷۳/۱۷۳ سبز**.

### CI و اعتبارسنجی
- فایل Workflow واقعی `.github/workflows/ci.yml` (جایگزین windows-ci.yml): اجرا روی push به `develop` و PRهای مرتبط؛ دو job — لینوکس (lint + typecheck + next build + pytest کامل + تست‌های agent + release.sh + build-windows.sh با راستی‌آزمایی زندهٔ کامل) و ویندوز (نصب + typecheck + build UI + تست‌های agent شامل رگرسیون UI + کامپایل EXE + **اجرای واقعی خود EXE** روی windows-latest با چک‌های زندهٔ امنیتی/UI). وضعیت push این فایل به‌دلیل مجوز `Workflows` توکن فعلی جداگانه و صادقانه گزارش می‌شود.
- بستهٔ Windows از همین کامیت با چک‌های رگرسیون امنیتی تازه ساخته و بازبینی می‌شود (SHA-256 در Release).

### محدودیت‌های صادقانه
- اجرای واقعی EXE روی ویندوزِ واقعی همچنان به اجرای CI وابسته است (نیازمند افزودن فایل workflow به remote — مجوز `Workflows` در توکن) یا یک ویندوز واقعی. شبیه‌سازی لینوکسی هرگز معادل آن معرفی نمی‌شود.
- این نسخه Beta است؛ انتقال به `main` و انتشار نسخهٔ پایدار فقط با تصمیم صریح مالک مخزن انجام می‌شود.

## [0.3.2] — ۲۰۲۶-۱۰-۲۵ — «رفع باگ UI ویندوزی»

### باگ گزارش‌شده
اجرأ HeadscaleEasyManager v0.3.1 روی Windows و بازکردن نشانی Desktop UI، به‌جای رابط گرافیکی این JSON را نشان می‌داد: `{"ok":true,"service":"hem-agent","version":"0.3.1"}`.

### علت ریشه‌ای
در باینری کامپایل‌شدهٔ bun، `import.meta.dir` به فایل‌سیستم مجازی باندل اشاره می‌کند؛ نشانگر آن روی لینوکس `/$bunfs/root` است اما روی ویندوز `C:\$bunfs\root` (حرف درایو + بک‌اسلش). بررسی `startsWith("/$bunfs")` فقط پوزیکس را می‌شناخت ← روی ویندوز `exeDir` به fs مجازی اشاره می‌کرد ← پوشهٔ `ui/` (که کنار EXE بسته‌بندی می‌شود، نه داخل آن) پیدا نمی‌شد ← مسیر fallbackِ `GET /` در api.ts به‌جای UI، JSON سلامت برمی‌گرداند. بستهٔ ZIP سالم بود (ui/index.html موجود) — باگ فقط در حل مسیر داخل EXE بود؛ روی لینوکس (کامپایل و راستی‌آزمایی زندهٔ build-windows.sh) مسیر پوزیکس درست تشخیص داده می‌شد و همین باعث شده بود باگ فقط روی ویندوز ظاهر شود.

### اصلاح
- `src/exepath.ts` (واحد مشترک): تشخیص باینری کامپایل‌شده با «عضویت `$bunfs` در مسیر» به‌جای پیشوند مطلق پوزیکس؛ `programDir()` = `dirname(process.execPath)` در حالت باندل، پوشهٔ سورس در حالت توسعه.
- `index.ts`: حل مسیر ui/ از `programDir`؛ نبودِ ui/ دیگر بی‌صدا رد نمی‌شود — لاگ خطای صریح (`UI NOT FOUND — expected ui/ at: …`) + راهنمایی؛ لاگ اجرا حالا مسیر واقعی ui را می‌گوید (`ui: served (مسیر)` / `ui: MISSING (expected مسیر)`).
- `src/api.ts`: حذف پاسخ JSON مبهم در `GET /`؛ وقتی UI موجود نیست پاسخ **503 text/html با صفحهٔ خطای فارسی روشن** است (علت + مسیر جست‌وجوشده + راه‌حل گام‌به‌گام) و همان رخداد در لاگ سرور ثبت می‌شود. ترتیب middlewareها تغییر نکرد: تبادل یک‌بارمصرف `?token=` → 303 + کوکی جلسه‌ای → `GET /` همان مسیر را با index.html پاسخ می‌دهد؛ `/api/health` کاملاً جدا و همیشه JSON است.
- `src/config.ts`: همان تشخیص کج برای کاندید dev نصب‌کننده هم اصلاح شد (روی ویندوز کاندید بی‌معنا نمی‌سازد).

### تست‌های رگرسیون (جدید)
- `test/exepath.test.ts` (۱۴ تست): قفل سناریوی ویندوزی `C:\$bunfs\root` بدون نیاز به ویندوز — با منطق قدیمی قطعاً fail می‌شود.
- `test/ui-serving.test.ts` (۱۱ تست): UI موجود → `GET /` = 200 text/html با محتوای واقعی (پس از تبادل توکن)؛ UI غایب → 503 text/html صفحهٔ خطای روشن «نه JSON مبهم»؛ `/api/health` در هر دو حالت JSON صحیح.
- `test/packaged.test.ts` (۶ تست): کامپایل واقعی باینری با `bun build --compile` + چیدمان بستهٔ رسمی (`ui/` و `installer/` کنار باینری) + اجرا + اثبات زندهٔ `GET /` = text/html واقعی، `GET /api/health` = JSON، لاگ `ui: served` با مسیر کنار باینری (نه $bunfs).
- `packaging/build-windows.sh`: دو چک زندهٔ جدید — `GET /` باید `Content-Type: text/html` باشد و بدنه هرگز JSON سلامت نداشته باشد.
- CI (`windows-ci.yml`): سه فایل رگرسیون به تست‌های قابل‌حمل هر دو job اضافه شد؛ در job ویندوز بعد از build UI اجرا می‌شوند تا `packaged` از UI واقعی استفاده کند؛ چک `Content-Type: text/html` صریح به مرحلهٔ «اجرای واقعی EXE» اضافه شد.

### آزموده‌نشده (صادقانه)
- اجرای واقعی EXE روی خودِ ویندوز: نیازمند فعال‌سازی CI (توکن فعلی مجوز Workflows ندارد — push فایل workflow رد می‌شود) یا یک ویندوز واقعی. پوشش موجود: تست مسیر ویندوزی به‌صورت قطعی (exepath)، اجرای واقعی باینری هم‌سورس روی لینوکس (packaged + build-windows.sh) و CI آمادهٔ اجرا روی windows-latest.

## [0.3.1] — ۲۰۲۶-۱۰-۲۴ — «فاز اصلاح پیش از انتشار»

### ساختار Git و انتشار (§۲ وظیفه)
- مخزن پایتون از gitlinkِ بدون `.gitmodules` به ساختار اصلی منتقل شد (fold) — clone تمیز حالا کل محصول را دارد؛ تاریخچهٔ ۷ کامیت آن در شاخهٔ `archive/hem-python` حفظ شد.

- خروجی‌های build و داده‌های توسعه هرگز وارد گیت/بسته نمی‌شوند: `.env`، `db/`، `prisma/`+`src/lib/db.ts` (اسکلت مرده — محصول پایگاه‌داده ندارد)، `download/`، `ui-out/` — release.sh با allowlist + خودآزمایی (حالا شامل ui-out/prisma/db.ts) و `git archive HEAD:headscale-easy-manager`.

### مسیر نصب‌کننده (§۱ وظیفه)
- مسیر توسعه‌دهندهٔ `/home/z/my-project/headscale-easy-manager` از همهٔ مسیرهای اجرایی حذف شد. زنجیرهٔ حل: `HEM_PROJECT_ROOT` → `installer/` کنار فایل اجرایی (بستهٔ ویندوزی آن را دارد) → checkout توسعه؛ اگر هیچ‌کدام نبود، خطای روشن با فهرست همهٔ مسیرهای امتحان‌شده — هرگز «آماده/موفق» اعلام نمی‌شود (`installerRootStatus` + لاگ صادقانهٔ راه‌اندازی).
- بستهٔ ویندوزی حالا `installer/` را کنار exe بسته‌بندی می‌کند؛ UI همیشه از ابتدا ساخته می‌شود (بدون بازاستفادهٔ `ui-out`).

### امنیت agent (§۴ وظیفه)
- **WebSocket بدون احراز هویت** (آسیب‌پذیری واقعی) بسته شد: اتصال socket.io بدون هدر/کوکی معتبر بلافاصله قطع می‌شود و هیچ رویداد حساسی نمی‌گیرد.
- تبادل `?token=` **یک‌بارمصرف** شد: کوکی جلسه‌ای HttpOnly/SameSite=Strict (بدون Max-Age) + 303 که نشانی را بدون token تمیز می‌کند؛ بازیابی لینک از تاریخچهٔ مرورگر دیگر کوکی نمی‌سازد. `token` در query هرگز روش احراز هویت API نیست. مقایسه‌ها timing-safe شدند.
- تست‌های مثبت/منفی جدید: `test/auth.test.ts` (HTTP/Bootstrap/WS — ۱۹ تست).

### بازیابی و پایداری (§۵ وظیفه)
- `test/recovery.test.ts` (agent): لغوی واقعیِ وسط عملیات روی SSH زنده + نتیجهٔ صادقانهٔ «لغوشده» (هرگز موفق جعلی) + اجرای دوباره پس از خطا.
- `tests/test_recovery_rerun.py`: خطا → اصلاح → دوباره → موفقیت واقعی ۱۷گامی؛ اجرای مجدد → همان خروجی (idempotent در سطح dry-run).

### CI (§۳.۴ وظیفه)
- GitHub Actions با دو job: **windows** (کامپایل و اجرای واقعی hem-manager.exe روی windows-latest: توکن یک‌بارمصرف، 401/200، installer/ بسته‌بندی‌شده، UI فارسی، SHA-256) و **linux** (clone تمیز: lint/typecheck/docs/build/pytest/release/build-windows).

### آزموده‌نشده (صادقانه)
- نصب واقعی روی اوبونتوی تازه با systemd: در سندباکس/CI ممکن نیست (systemd نیست) — dry-run و منطق واقعی با ۱۰۵+ تست پوشش داده شده؛ اجرای کامل نیازمند VPS آزمایشی واقعی است.
- اتصال SSH به VPS واقعی در CI آزموده نمی‌شود (نیازمند سرور واقعی)؛ در سندباکس با سرور آزمایشی ۲۲۲۲ پوشش داده شده است.

- پایتون: ۱۰۳ تست پاس (واحد/ماژول — نصب‌کننده، چک‌سام، سلامت صادقانه، فایروال، rollback ارتقا، پشتیبان per-file)
- hem-agent: ۸۳ تست پاس با سرور SSH آزمایشی واقعی (ssh2) و باینری واقعی headscale 0.29.5

### محدودیت‌های شناخته‌شده
- تست یکپارچهٔ واقعی نصب روی اوبونتوی تمیز (apt/systemd/UFW/Caddy واقعی) همچنان به VPS آزمایشی نیاز دارد — در محیط توسعه با سرور SSH آزمایشی و dry-run واقعی پوشش داده شده است.
- ارتقا باید نسخه‌به‌نسخه انجام شود (قید رسمی Headscale)؛ `hsctl update` هشدار می‌دهد.

## [0.1.0] — نسخه اول

### افزوده‌شده
- نصب‌کننده تعاملی و خودکار Headscale v0.29.5 روی Ubuntu Server 22.04/24.04 (amd64/arm64)
- بررسی پیش‌نیازها (preflight): سیستم‌عامل، معماری، دیسک، RAM، sudo، پورت‌ها، سرویس‌های موجود
- تشخیص و احترام به سرویس‌های موجود (Caddy/Headscale/nginx/… ) با پشتیبان‌گیری قبل از هر تغییر
- پیکربندی Headscale + Caddy (TLS خودکار) + فایروال UFW با حفظ دسترسی SSH
- ابزار مدیریت `hsctl`: status, doctor, logs, users, devices, preauth, routes, backup, restore, update, config, cameras, learn, explain, report, uninstall
- پشتیبان‌گیری/بازیابی کامل (SQLite با .backup امن + کلیدها + پیکربندی + manifest)
- مدیریت دوربین‌های مداربسته و دستگاه ضبط Dahua از طریق Subnet Router
- مرکز آموزش فارسی (۱۴ فصل) به‌همراه `hsctl learn` و `hsctl explain`
- گزارش تشخیصی قابل‌ارسال با حذف خودکار اطلاعات حساس
- حالت `--dry-run` برای نمایش تغییرات بدون اعمال

### محدودیت‌های شناخته‌شده
- تست‌های یکپارچه واقعی (systemd/apt/UFW/Caddy) باید روی VPS آزمایشی Ubuntu 22.04/24.04 اجرا شوند؛
  در محیط توسعه فقط منطق (parserها، تولید پیکربندی، state، پشتیبان) تست واحد شده است.
- ارتقا باید نسخه‌به‌نسخه انجام شود (قید رسمی Headscale)؛ `hsctl update` هشدار می‌دهد.
