# فصل ششم: دسترسی از بیرون به شبکه دفتر

در این فصل یاد می‌گیرید:

- سناریوی کامل دسترسی به CRM دفتر از هر جای دنیا
- چه دستگاهی برای نقش «مسیریاب زیرشبکه» مناسب است
- در ۷ گام: نصب، اعلام رنج، فعال‌سازی هدایت بسته، تأیید روی سرور، پذیرش روی کلاینت‌ها، تست و درک مسیر برگشت
- چرا جواب‌ها به گوشی شما برمی‌گردند و چه زمانی برنمی‌گردند
- عیب‌یابی سریع وقتی چیزی کار نکرد

این فصل، قلب آموزش و دلیل اصلی ساخت این پروژه است: بعد از همین فصل، از کافه، فرودگاه یا خانه، آدرس `http://192.168.1.220:800` را باز می‌کنید و CRM دفتر جلوی شماست.

> 🔎 **چه چیزی را کجا اجرا می‌کنیم؟** مراحل این فصل روی **سه دستگاه متفاوت** اجرا می‌شوند؛ این جدول را یک بار ببینید تا هیچ‌وقت جاها را قاطی نکنید (توضیح کامل محیط‌ها: فصل چهارم، بخش ۴.۰):
>
> | مرحله | روی کدام دستگاه؟ | محیط اجرا |
> |---|---|---|
> | گام ۱ تا ۳ (نصب کلاینت، اعلام رنج، IP Forwarding) | دستگاهِ دفتر که نقش مسیریاب را دارد (در این آموزش: لینوکسی) | ترمینال لینوکسی خودِ دستگاه |
> | گام ۴ (تأیید Route) | سرور VPS | نشست SSH از ویندوز/لینوکس/مک، یا پنل برنامهٔ ویندوزی (فصل ۱۶) |
> | گام ۵ (پذیرش Route) | دستگاه‌های مصرف‌کننده (لپ‌تاپ و…) | لینوکس: ترمینال / ویندوز: هیچ کاری لازم نیست (پیش‌فرض فعال) |
> | گام ۶ (تست) | گوشی/لپ‌تاپ بیرون از دفتر | مرورگر، پینگ، اپ Tailscale |
>
> دستورهای مربوط به سرور (مثل `hsctl routes approve`) هرگز روی ویندوز شما اجرا نمی‌شوند؛ از ویندوز با `ssh` به سرور وصل شوید و در نشست سرور اجرا کنید (بخش ۴.۲) یا از پنل گرافیکی استفاده کنید.

## ۶.۱ سناریوی کامل

قطعات صحنه — همه را از فصل‌های قبل می‌شناسید:

```text
     ┌─────────────────────────────────────────────────────┐
     │                     اینترنت                          │
     └───────┬─────────────────────────────┬───────────────┘
             │                             │
   ┌─────────┴──────────┐        ┌─────────┴─────────┐
   │ VPS شما            │        │ گوشی / لپ‌تاپ     │
   │ headscale.         │        │ (بیرون از دفتر)   │
   │ example.com        │        │ کلاینت Tailscale  │
   │ سرور هماهنگ‌سازی    │        │ VPN: 100.64.0.2   │
   └────────────────────┘        └───────────────────┘
             ▲                             ▲
             │  CONTROL PLANE              │ DATA PLANE
             │  (فقط هماهنگی)              │ (تونل مستقیم)
             │                             │
   ┌─────────┴─────────────────────────────┴───────────────┐
   │                      دفتر                             │
   │  ┌──────────────────────────────────────┐             │
   │  │ مسیریاب زیرشبکه (Subnet Router)      │             │
   │  │ مینی‌PC لینوکسی، همیشه‌روشن          │             │
   │  │ LAN: 192.168.1.10  |  VPN: 100.64.0.1│             │
   │  └──────────────┬───────────────────────┘             │
   │                 │ عضو هر دو دنیا                      │
   │        ┌────────┴─────────────────────┐               │
   │        │   شبکهٔ LAN دفتر 192.168.1.0/24│              │
   │        │   ├── سرور CRM 192.168.1.220:800              │
   │        │   ├── NVR دوربین 192.168.1.108                │
   │        │   └── چاپگر، NAS و بقیه…      │               │
   │        └────────────────────────────────┘               │
   └────────────────────────────────────────────────────────┘
```

منطق کار ساده است: یک دستگاهِ **داخل دفتر** عضو شبکهٔ VPN می‌شود و اعلام می‌کند «من به کل شبکهٔ `192.168.1.0/24` دسترسی دارم». سرور این ادعا را تأیید می‌کند و به بقیهٔ اعضا می‌گوید: «برای رسیدن به `192.168.1.x` بروید سراغ این دستگاه.» به این دستگاه، **مسیریاب زیرشبکه (Subnet Router)** می‌گوییم — «سفیرِ» کل شبکهٔ دفتر در VPN.

نتیجه: لازم نیست روی CRM یا دوربین یا چاپگر چیزی نصب کنید؛ فقط همین یک دستگاه، پل می‌شود.

## ۶.۲ انتخاب دستگاهِ مسیریاب زیرشبکه

هر دستگاهی این نقش را نمی‌تواند بازی کند. سه شرط:

1. **همیشه‌روشن باشد:** اگر دستگاه خاموش شود، دسترسی همه به دفتر قطع می‌شود. پس لپ‌تاپ شخصی که شب خاموشش می‌کنید، انتخاب بدی است.
2. **داخل دفتر باشد** (وصل به همان LAN هدف): باید بتواند خودش به `192.168.1.220` برسد تا بتواند پل بزند.
3. **ترجیحاً لینوکس باشد:** راه‌اندازی روی لینوکس ساده، پایدار و بدون‌دردسر است و دستورهای این آموزش دقیقاً برای آن است.

انتخاب‌های رایج و خوب: یک **مینی‌PC** کم‌مصرف (هر چیزی که بتواند اوبونتو نصب کند)، یک سرور ابری کوچکِ داخل دفتر، یا همان کامپیوتری که روزی روی آن سرور CRM را اجرا کرده‌اید (اگر لینوکسی و همیشه‌روشن است). در ادامهٔ این فصل اسمش را `office-router` می‌گذاریم و IP داخلی‌اش را `192.168.1.10` فرض می‌کنیم.

> 🔎 **اگر دستگاه دفتر شما ویندوزی است؟ صادقانه:** مستندات رسمی Tailscale، «مسیریاب زیرشبکه» را برای لینوکس و macOS مستند کرده‌اند و این آموزش هم فقط همان مسیر لینوکسی را پوشش می‌دهد و آزموده است. فرمانِ اعلام رنج (`tailscale up --advertise-routes=...`) در CLI ویندوز هم وجود دارد، اما «هدایت IP» در ویندوز باید جداگانه و از طریق تنظیمات خود ویندوز فعال شود و این ترکیب، نه در مستندات رسمی Tailscale آمده و نه توسط این پروژه آزمایش شده است — پس آن را به‌عنوان روش پشتیبانی‌شده معرفی نمی‌کنیم. اگر دستگاه ویندوزی دارید، برای این نقش یک مینی‌PC لینوکسی (حتی قدیمی و کم‌مصرف) بگذارید. **WSL هم برای این نقش مناسب نیست** — شبکهٔ WSL خودش پشت NAT ویندوز است و مسیریابی پایدار از آن انتظار نمی‌رود.

## ۶.۳ گام ۱ — نصب کلاینت Tailscale و اتصال به سرور

روی دستگاه دفتر (لینوکسی — طبق توضیح همین فصل، این نقش باید لینوکسی باشد)، کلاینت رسمی را نصب کنید (همان دستور رسمی فصل پنجم):

```bash
curl -fsSL https://tailscale.com/install.sh | sh
```

توضیح: اسکریپت نصب رسمی، بستهٔ کلاینت Tailscale را برای توزیع شما نصب می‌کند. (معادل همین کار برای یک دستگاه **ویندوزی** مصرف‌کننده — نه مسیریاب — در فصل هفدهم آمده است: نصب با Winget و اتصال با `tailscale login`.)

و دستگاه را به سرور وصل کنید (جریان تأیید در فصل پنجم، بخش ۵.۶) — روی همان دستگاه دفتر:

```bash
sudo tailscale up --login-server https://headscale.example.com
```

توضیح خط‌به‌خط:

- `sudo tailscale up` : روشن‌کردن کلاینت و شروع عضویت در سرورِ مشخص‌شده
- `--login-server https://headscale.example.com` : آدرس سرور کنترل خودِ شما

مرورگر را باز کنید، `AUTH_ID` را بگیرید و روی سرور تأییدش کنید (این دستور روی **سرور** اجرا می‌شود — از ویندوز: داخل نشست SSH یا با الگوی یک‌خطی بخش ۴.۰):

```bash
headscale auth register --user admin --auth-id <AUTH_ID>
```

از ویندوز، معادل یک‌خطی:

```powershell
ssh ubuntu@203.0.113.10 "headscale auth register --user admin --auth-id <AUTH_ID>"
```

از این لحظه، `office-router` مثل گوشی و لپ‌تاپ، یک عضو سادهٔ شبکهٔ VPN است (فعلاً فقط برای خودش، نه بقیه).

## ۶.۴ گام ۲ — اعلام رنج شبکهٔ دفتر

حالا به کلاینت می‌گوییم «تو پل هستی» — یعنی رنج `192.168.1.0/24` را **اعلام (Advertise)** کند — روی همان دستگاه دفتر (لینوکسی):

```bash
sudo tailscale up --login-server https://headscale.example.com --advertise-routes=192.168.1.0/24
```

توضیح خط‌به‌خط:

- `sudo tailscale up` : اجرای مجدد کلاینت با تنظیمات جدید
- `--login-server https://headscale.example.com` : همان سرور شما
- `--advertise-routes=192.168.1.0/24` : «من مسیریابِ این رنج هستم» — یعنی می‌توانم بسته‌هایی که مقصدشان `192.168.1.x` است را تحویل بدهم

> اگر دستگاه از قبل عضو بوده و فقط می‌خواهید رنج را اضافه کنید، لازم نیست دوباره `up` کامل بزنید؛ همین کافی است:
>
> ```bash
> sudo tailscale set --advertise-routes=192.168.1.0/24
> ```

تا اینجا فقط «اعلام» کردیم. سرور هنوز به این ادعا اعتماد نکرده — این عمداً طراحی شده تا هرکس نتواند مسیر شبکهٔ شما را بدزدد. تأیید در گام ۴.

## ۶.۵ گام ۳ — فعال‌سازی هدایت بسته‌ها (IP Forwarding)

دستگاه دفتر الان باید بسته‌ای که از تونل می‌آید را به LAN بدهد و جوابش را برگرداند. لینوکس به‌صورت پیش‌فرض این کار را نمی‌کند؛ باید «هدایت IP (IP Forwarding)» را روشن کنیم — روی همان دستگاه دفتر:

```bash
echo 'net.ipv4.ip_forward = 1' | sudo tee -a /etc/sysctl.d/99-tailscale.conf
echo 'net.ipv6.conf.all.forwarding = 1' | sudo tee -a /etc/sysctl.d/99-tailscale.conf
sudo sysctl -p /etc/sysctl.d/99-tailscale.conf
```

> 🔎 **این گام مخصوص لینوکس است و معادل ویندوزیِ پشتیبانی‌شده‌ای در این آموزش ندارد.** «هدایت IP» قابلیتی از خود سیستم‌عامل است و روش فعال‌سازی‌اش در هر سیستم‌عامل متفاوت است؛ طبق توضیح بخش ۶.۲، نقش مسیریاب زیرشبکه باید روی دستگاه لینوکسی باشد و این سه خط فقط در لینوکس معنا دارد (و چون در فایل پیکربندی ذخیره می‌شود، بعد از ری‌استارت هم برقرار می‌ماند).

توضیح خط‌به‌خط:

- خط ۱: نوشتن تنظیم `net.ipv4.ip_forward = 1` (فعال‌سازی هدایت IPv4) در فایل پیکربندی دائمی `/etc/sysctl.d/99-tailscale.conf` — `tee -a` یعنی «به انتهای فایل اضافه کن»
- خط ۲: همین کار برای هدایت IPv6
- خط ۳: اعمال فوری همان فایل پیکربندی (`sysctl -p`) — بدون نیاز به ری‌استارت

نکتهٔ خوب: این تنظیم در فایل ذخیره می‌شود، پس بعد از ری‌استارت دستگاه هم برقرار می‌ماند.

## ۶.۶ گام ۴ — تأیید Route روی سرور

حالا روی **سرور** (از طریق SSH — فصل چهارم؛ این دستورها هیچ‌کدام روی ویندوز شما اجرا نمی‌شوند) وضعیت مسیرهای اعلام‌شده را ببینید:

```bash
hsctl routes list
```

از ویندوز، معادل یک‌خطی (بخش ۴.۰):

```powershell
ssh ubuntu@203.0.113.10 "hsctl routes list"
```

یا از رابط گرافیکی برنامهٔ ویندوزی: بخش **«مسیرها»** همان جدول را نشان می‌دهد و دکمهٔ تأیید دارد ([فصل شانزدهم](16-amoozesh-panel.md)).

یا با دستور خام headscale:

```bash
headscale nodes list-routes
```

خروجی نمونه (ستون‌ها طبق Headscale نسخهٔ ۰.۲۹):

```text
ID | Hostname       | Approved | Available       | Serving (Primary)
1  | office-router  |          | 192.168.1.0/24  |
```

یعنی: دستگاه شمارهٔ ۱ رنج `192.168.1.0/24` را «پیشنهاد» کرده ولی ستون Approved خالی است — هنوز تأیید نشده. تأیید کنید (روی سرور):

```bash
hsctl routes approve 1 --routes 192.168.1.0/24
```

از ویندوز، معادل یک‌خطی:

```powershell
ssh ubuntu@203.0.113.10 "sudo hsctl routes approve 1 --routes 192.168.1.0/24"
```

(چون این دستور sudo است، اگر سرور برای sudo رمز بخواهد، یا نشست تعاملی SSH باز کنید یا `ssh -t` بزنید — بخش ۴.۰.)

یا معادل خام:

```bash
headscale nodes approve-routes --identifier 1 --routes 192.168.1.0/24
```

توضیح خط‌به‌خط:

- `approve` / `approve-routes` : «مسیر پیشنهادی فلان دستگاه را تأیید می‌کنم»
- `1` / `--identifier 1` : شمارهٔ دستگاه از جدول بالا (ID)
- `--routes 192.168.1.0/24` : رنجی که تأیید می‌شود (چند رنج را با کاما جدا می‌کنند؛ مثلاً اگر روزی دو شبکهٔ دفتر داشتید)

خروجی دوباره `hsctl routes list` بگیرید؛ حالا باید رنج در ستون Approved (و Serving) ظاهر شود:

```text
ID | Hostname       | Approved       | Available       | Serving (Primary)
1  | office-router  | 192.168.1.0/24 | 192.168.1.0/24  | 192.168.1.0/24
```

## ۶.۷ گام ۵ — پذیرش Route روی کلاینت‌های مصرف‌کننده

یک قدم آخر: به دستگاه‌هایی که می‌خواهند «از» این پل استفاده کنند بگویید مسیرهای اعلامی را بپذیرند.

**روی دستگاه‌های لینوکسی** (لپ‌تاپ لینوکسی، سرور دوم و…):

```bash
sudo tailscale set --accept-routes
```

**روی ویندوز — هیچ دستوری لازم نیست.** طبق مستندات رسمی Tailscale، در ویندوز (و اندروید و iOS و هر دو نوع کلاینت مک) پذیرش مسیرهای اعلامی **به‌صورت پیش‌فرض روشن** است؛ اگر روزی روی ویندوز چیزی کار نکرد، در برنامهٔ Tailscale (آیکون سینی کنار ساعت) مطمئن شوید گزینهٔ Subnet routes فعال باشد — معمولاً هست. اگر خواستید مثل لینوکس صریح بگویید، همان دستور در PowerShell ویندوز هم هست (بدون sudo):

```powershell
tailscale set --accept-routes
```

توضیح: «مسیرهایی که سرور تأیید کرده را در جدول مسیریابی من بگذار» — از این لحظه، جدول مسیریابی دستگاه یک سطر تازه دارد: «برای `192.168.1.x` برو سراغ تونل».

گوشی اندرویدی شما هیچ دستوری نمی‌خواهد؛ از لحظهٔ تأیید Route روی سرور، پل آماده است.

## ۶.۸ گام ۶ — تست نهایی (لحظهٔ حقیقت!)

گوشی را از وای‌فای دفتر **قطع کنید** (اینترنت همراه — چون می‌خواهیم واقعاً «از بیرون» تست کنیم) و Tailscale را روشن نگه دارید. سپس:

**تست ۱ — پینگ سرور CRM:**

روی لینوکس/مک (پینگ تا وقتی خودتان با Ctrl+C قطعش نکنید ادامه دارد):

```bash
ping 192.168.1.220
```

روی ویندوز (PowerShell یا CMD — پیش‌فرض فقط ۴ بسته می‌فرستد و می‌ایستد؛ برای پینگ پیوسته مثل لینوکس، `-t` بدهید و با Ctrl+C قطع کنید):

```powershell
ping -t 192.168.1.220
```

خروجی مطلوب در ویندوز چیزی شبیه `Reply from 192.168.1.220: bytes=32 time=41ms TTL=63` است و در لینوکس شبیه `64 bytes from 192.168.1.220: icmp_seq=1 ttl=63 time=42.1 ms` — هر دو یعنی یکی: جواب برمی‌گردد.

(روی گوشی اندروید می‌توانید از داخل خود برنامهٔ Tailscale بخش Diagnostics/پینگ را ببینید، یا از ترمینال لپ‌تاپ وصل‌شده تست کنید.)

خروجی مطلوب (لینوکس):

```text
64 bytes from 192.168.1.220: icmp_seq=1 ttl=63 time=42.1 ms
64 bytes from 192.168.1.220: icmp_seq=2 ttl=63 time=39.8 ms
```

**تست ۲ — پینگ در سطح VPN** (اگر دوست دارید بدانید مسیر داده چطور می‌رود) — این دستور روی هر کلاینت Tailscale (لینوکس و ویندوز) یکسان است:

روی لینوکس:

```bash
tailscale ping office-router
```

روی ویندوز (PowerShell یا CMD):

```powershell
tailscale ping office-router
```

خروجی نمونه:

```text
pong from office-router (100.64.0.1) via 203.0.113.45:41231 in 21ms
```

**تست ۳ — باز کردن CRM در مرورگر:**

آدرس CRM را در مرورگر گوشی/لپ‌تاپ باز کنید:

```text
http://192.168.1.220:800
```

صفحهٔ ورود CRM دفتر ظاهر می‌شود. تمام — شما الان از بیرون دفتر، داخل شبکهٔ دفتر هستید.

## ۶.۹ گام ۷ — فایروال و مسیر برگشت: جواب‌ها چطور برمی‌گردند؟

بیایید صادقانه بفهمیم بستهٔ شما چه مسیری می‌رود و برمی‌گردد:

```text
 گوشی (بیرون)                    دفتر
 ─────────────────────────────────────────────────────────
 1. بستهٔ «درخواست CRM»
    مقصد: 192.168.1.220:800
              │
              │ تونل WireGuard (مستقیم یا رلهٔ DERP)
              ▼
       office-router (100.64.0.1)
              │ 2. هدایت به داخل LAN (IP Forwarding)
              │    و بازنویسی مبدا با IP خود دستگاه (SNAT)
              ▼
       سرور CRM (192.168.1.220)
       مبدا را می‌بیند: 192.168.1.10 (خودِ دستگاهِ دفتری)
              │ 3. جواب را برای همان مبدا می‌فرستد
              ▼
       office-router
              │ 4. جواب از همان تونل برمی‌گردد
              ▼
 گوشی: صفحهٔ CRM بارگذاری شد ✓
```

نکتهٔ ظریف و مهم مرحلهٔ ۳: سرور CRM «فکر می‌کند» با خودِ دستگاهِ دفتری (office-router) صحبت می‌کند — چون کلاینت Tailscale به‌صورت پیش‌فرض مبدا را با IPِ LAN دستگاهِ پل بازنویسی می‌کند (رفتاری به نام SNAT). پس جواب را به همان دستگاه می‌دهد و دستگاه هم از تونل به شما برمی‌گرداند. **به همین دلیل معمولاً هیچ تنظیم اضافه‌ای لازم نیست** — نه روی مودم دفتر، نه روی CRM؛ ترافیک از داخل LAN با IP دستگاهِ سرورِ VPN دفتر می‌آید و به همان برمی‌گردد.

چه زمانی این چرخه می‌شکند؟

- **ACL/فیلترینگ روی روتر دفتر:** اگر مودم/فایروال دفتر ترافیک بین دستگاه‌های LAN را محدود کرده باشد.
- **فایروال شخصی روی خود دستگاه CRM:** مثلاً اگر CRM روی ویندوزی اجرا می‌شود که فایروالش اجازهٔ اتصال به پورت 800 را از بیرون نمی‌دهد. راه‌حل: در فایروال آن دستگاه، اتصال به پورت 800 را مجاز کنید. اگر CRM ویندوزی است، با **PowerShell مدیریتی** روی همان دستگاه:

```powershell
New-NetFirewallRule -DisplayName "CRM port 800" -Direction Inbound -Protocol TCP -LocalPort 800 -Action Allow
```

یا از رابط گرافیکی: Control Panel ← Windows Defender Firewall ← Advanced Settings ← Inbound Rules ← New Rule (پورت TCP 800). بعد از افزودن قاعده، دوباره از تونل تست کنید.
- **دستگاه CRM خودش IP مشکل‌دار داشته باشد** (مثلاً آدرسش عوض شده باشد) — دوباره چک کنید `192.168.1.220` هنوز درست است.

## ۶.۱۰ عیب‌یابی سریع

اگر تست‌های گام ۶ جواب نداد، به ترتیب این ۵ سؤال را از خودتان بپرسید (هر پاسخ «نه»، مقصر بعدی را خالی می‌کند):

1. **Route روی سرور تأیید شده؟** — روی سرور `hsctl routes list` بزنید؛ رنج باید در ستون Approved باشد. (گام ۴)
2. **دستگاه مسیریاب آنلاین است؟** — از گوشی یا لپ‌تاپ `tailscale ping office-router` (روی ویندوز همین دستور در PowerShell/CMD) — اگر جواب نداد، دستگاه دفتر خاموش/آفلاین است یا قطع شده (`tailscale status` روی آن بزنید — روی لینوکس `sudo tailscale up` و روی ویندوز اپ را از سینی وصل کنید — اگر لازم بود).
3. **مسیریاب خودش به CRM می‌رسد؟** — روی خود `office-router` امتحان کنید: `ping 192.168.1.220` — اگر نرسید، مشکل در LAN دفتر است (کابل، آدرس اشتباه، VLAN).
4. **کلاینت مصرف‌کننده Route را پذیرفته؟** — لینوکس: `sudo tailscale set --accept-routes` (گام ۵)؛ ویندوز/اندروید/مک: پیش‌فرض روشن است (بخش ۶.۷).
5. **پورت درست است؟** — CRM روی پورت `800` است؛ آدرس کامل `http://192.168.1.220:800` را زدید؟ (بدون `:800` معمولاً صفحه‌ای نیست.) — اگر می‌خواهید از ویندوز مطمئن شوید پورت باز است، در PowerShell: `Test-NetConnection 192.168.1.220 -Port 800` (ستون `TcpTestSucceeded` باید `True` باشد).

بیشتر از این؟ جدول عیب‌یابی کامل در [فصل نهم: عیب‌یابی](09-eibyabi.md) منتظر شماست.

> **تأکید مهم مأموریت:** تأیید Route به‌تنهایی هیچ‌وقت کافی نیست. دو شرط دیگر باید واقعاً برقرار باشد: (۱) دستگاه مسیریاب باید **واقعاً به LAN دفتر دسترسی داشته باشد** (خودش بتواند CRM را پینگ کند)، و (۲) **مسیر برگشت** جواب‌ها درست باشد (بخش ۶.۹). اگر یکی از این دو نباشد، تأییدِ صدتایی هم روی سرور چیزی را عوض نمی‌کند.

## خلاصه فصل

- یک دستگاه همیشه‌روشن و لینوکسی داخل دفتر را «مسیریاب زیرشبکه (Subnet Router)» کردیم: سفیر کل رنج `192.168.1.0/24` در شبکهٔ VPN. (ویندوز و WSL برای این نقش معرفی نمی‌شوند — دلیل صادقانه در بخش ۶.۲.)
- گام ۱: نصب کلاینت رسمی و اتصال به سرور مثل هر دستگاه دیگری.
- گام ۲: اعلام رنج با `sudo tailscale up --login-server ... --advertise-routes=192.168.1.0/24` (یا `tailscale set --advertise-routes=...` برای دستگاه عضو قبلی) — روی دستگاه دفتر.
- گام ۳: فعال‌سازی هدایت IP با سه خط sysctl (دائمی و بدون ری‌استارت) — مخصوص لینوکس، بدون معادل ویندوزیِ پشتیبانی‌شده.
- گام ۴: تأیید روی سرور: `hsctl routes list` → `hsctl routes approve <ID> --routes 192.168.1.0/24` (معادل خام: `headscale nodes approve-routes --identifier <ID> --routes ...`)؛ از ویندوز: نشست SSH یا `ssh ... "sudo hsctl routes approve ..."` یا پنل گرافیکی.
- گام ۵: روی کلاینت‌های لینوکسی `sudo tailscale set --accept-routes`؛ ویندوز/اندروید/macOS به‌صورت پیش‌فرض می‌پذیرند (طبق مستندات رسمی Tailscale).
- گام ۶: از بیرون دفتر، `ping 192.168.1.220` (ویندوز: `ping -t`) و باز کردن `http://192.168.1.220:800` در مرورگر؛ تست پورت در ویندوز با `Test-NetConnection`.
- گام ۷: جواب‌ها چون (با بازنویسی مبدا/SNAT) از IPِ دستگاه دفتری به CRM می‌رسند، به همان برمی‌گردند — مشکل فقط با ACL روتر یا فایروال خود CRM پیش می‌آید.
- Route به‌تنهایی کافی نیست: دسترسی واقعی مسیریاب به LAN و مسیر برگشت سالم، دو شرط مکمل‌اند.

دسترسی به CRM دارید؛ حالا ببینیم «نود خروجی» چه دردی را دوا می‌کند و چرا (بر خلاف تصور خیلی‌ها) اصلاً لازمش ندارید: [فصل هفتم: Exit Node](07-exit-node.md)
